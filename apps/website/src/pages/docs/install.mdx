# Install

stage installs per user, without root, from its GitHub releases. Pick one mode:

- **Desktop**: the [desktop app](/docs/desktop) with its CLI/server. It starts the server as a per-user service for you.
- **Headless**: the CLI/server only, for a remote machine or one without a display. You run the server as a [per-user service](/docs/deploy#run-as-a-service).

Both modes put the same `stage` CLI on your `PATH`. The CLI/server is one binary: `stage serve` (or `stage` with no arguments) runs the server, and every other subcommand is the CLI that [agents](/docs/agents) use.

## Install

```sh
# desktop
curl -fsSL https://raw.githubusercontent.com/flexdinesh/stage/main/scripts/install.sh | sh
# CLI/server only
curl -fsSL https://raw.githubusercontent.com/flexdinesh/stage/main/scripts/install.sh | sh -s -- --headless
```

| Flag | Meaning |
|---|---|
| `--headless` | CLI/server only (no desktop app, no GTK/WebKit needed) |
| `--version X.Y.Z` | install that version instead of the latest stable one (the only way to get a pre-release) |
| `--cli-name NAME` | the CLI's name in `~/.local/bin` (default `stage`) |

The script detects the OS (Linux, macOS) and CPU (amd64, arm64), downloads the latest stable release's manifest, checksums and the one archive this machine needs, checks its sha256, and runs that release's own `stage install`. That command verifies the release again and only then installs. Any failed check exits 11 with nothing installed. Never run it as root.

Releases are not signed: the checks catch corrupt, truncated or substituted downloads and wrong-platform releases; trust in the release itself rests on the GitHub account and HTTPS.

Open Settings to connect OpenCode or [pair T3](/docs/t3). Desktop: open stage from your app launcher. Headless: `stage service start` ([Headless server](/docs/deploy#run-as-a-service)).

## Requirements

- Linux or macOS, amd64 or arm64. Windows is not supported.
- **Linux desktop**: glibc, GTK 3 and WebKitGTK 4.1. When they are missing the install stops (exit 7) and prints the install command for your distribution (`apt-get`, `dnf`, `pacman`, `zypper`); it never installs packages itself.
- **macOS**: 12 or later. Releases ship the Mac desktop app only once it can be signed and notarized; until then use `--headless` on a Mac.
- **Headless**: nothing else (a static binary).
- For execution, an existing T3 Code or OpenCode V2 service that Stage can reach.

## What it installs

| What | Linux | macOS |
|---|---|---|
| App (desktop or headless) | `~/.local/lib/stage/app/` | desktop: `~/Applications/Stage.app`; headless: `~/.local/lib/stage/app/` |
| Previous version (one, for rollback) | `~/.local/lib/stage/app.prev` | `~/Applications/Stage.app.prev` (headless: `app.prev`) |
| CLI on `PATH` | `~/.local/bin/stage`, a link to the app's `bin/stage` | same |
| Desktop entry (launcher, icon, `stage://` links) | `$XDG_DATA_HOME/applications/stage-desktop.desktop` | the app bundle |
| Install record | `~/.local/lib/stage/install.json` | same |

The app's path never changes across updates, so the service and the desktop entry keep working. Your data, config (`service.env`), logs, database backups and desktop preferences live elsewhere and are never touched by install, update or uninstall.

:::note
The installer replaces a file at the CLI or desktop entry path only when it put it there. Anything else stops the install (exit 7) with the fix: an older `stage` built from a checkout (`mise run install-cli`, a development build) or another desktop entry. Remove it, or install under another name with `--cli-name`.
:::

Release assets also include `.deb`, `.rpm` and PKGBUILD packages of the Linux desktop app (installed to `/opt/stage-desktop`). Update those with your package manager; `stage update` only updates installer installs.

## Update

```sh
stage update                    # latest stable release, same mode (headless stays headless)
stage update --check            # installed, latest and running server versions
stage update --version 1.4.0    # a specific version, also a pre-release or an older one
```

Updates are explicit: nothing checks or updates in the background. Rerunning the install script does the same as `stage update`.

- **What restarts**: the per-user service restarts only if it was running this install's CLI. In-flight requests drain for up to 100s and no task is relaunched. T3 and its running agents are never touched. A running desktop app is quit and reopened.
- **Database**: the new server migrates the database when it starts, after copying it to `<data dir>/backups/` (the newest 3 are kept).
- **Failed start**: with no new migrations the installer rolls back to the previous version (exit 12). With new migrations it keeps the new version (exit 13) and prints the log tail and backup path; check `stage service logs`, fix the cause and run `stage service restart`.
- **Diagnostics**: `stage version` shows the binary and its installation; `stage service status` shows the running server's version.

## Uninstall

```sh
stage uninstall
```

Quits the desktop app, removes the service definition, the app and its previous version, the CLI link and the desktop entry. It keeps and lists your data dir, config (`service.env`), logs, database backups and desktop preferences; delete them yourself to remove everything. On macOS 13+, remove a leftover login item in System Settings > General > Login Items.

`stage install`, `update` and `uninstall` exit 0 when done, 1 on failure, 3 when another install is running, 7 when unsupported (not an installer install, a file it does not own, missing requirements, root), 10 on network errors, 11 when verification failed, 12 when rolled back and 13 when kept after a failed start. Each takes `--json`.
