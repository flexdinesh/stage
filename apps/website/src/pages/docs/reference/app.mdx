# The app

The same app runs in a browser (installable as a PWA) and in the desktop app. This page lists its pages and controls. The ideas behind them: [Concepts](/docs/concepts).

## Navigation and project scope

- **Sidebar** (laptop width): Search, New task, then Dashboard, Tasks, Trees and Schedules, then your projects. On a phone: a project chip in the top bar and bottom tabs.
- **Project scope**: pick a project to scope Dashboard, Tasks, Trees and Schedules to it. The choice is remembered on each device.
- **Projects list**: projects with open work are listed by recent activity with their counts (needs input, waiting on you, running). Pin the ones you want on top; the rest fold away as quiet projects.
- **Back and forward**: on a laptop, the sidebar header holds back and forward arrows in the desktop app and the installed web app (a browser tab uses the browser's own). Right-click or long-press an arrow to jump further back through recent pages. On a phone, Back sits in the top bar on any page off the tabs. Both move through the app's own history only.
- **Desktop shortcuts**: `Cmd+[` / `Cmd+]` (`Alt+Left` / `Alt+Right` on Linux) and the mouse side buttons go back and forward.
- **Page titles**: every page sets the tab title to its name (for example `Fix login redirect · stage`), so browser history lists pages by name.

### Connection status

The sidebar's bottom row starts with a status button that sums up your connections: "All connected", the one thing that needs you, or how many do. It covers every set-up connection on every machine; a worker that is offline or needs an update counts as a problem. Click it for each connection's state, one section per machine when there are several. On a phone the same list is on More, and the More tab shows a square while something needs attention.

## Dashboard

What needs you, across projects (or the scoped project):

- Needs input, finished runs awaiting your completion, ready tasks and failures, then In flight counts (running, scheduled in the next 24h, backlog) that open Tasks.
- Finished rows offer one-click **Complete** (an inline confirm when it would auto-start dependents; the row stays about 6s with Undo) and **Review** (the full drawer). The group header offers **Complete all**.
- Tree members carry a tree chip.
- While nothing is connected, a **Connect a harness** alert links to Settings > Connections. Each connection problem the status button shows (an expired pairing, an unreachable service) is an alert at the top with **Fix in Settings**.
- External harness alerts stay in the notifications inbox.

The Dashboard works offline for planning.

## Tasks

Browse all work: Open, Closed or All, every task by state, or only tasks not in a tree.

- A count strip filters to one group. Completed holds the last 7 days. Scheduled (next 24h) lists upcoming scheduled starts.
- Tree tasks link their tree (opened with the task selected).
- **New task**: under the prompt, a **Harness** group (titled with the harness name, "Harness · OpenCode") holds what the chosen connection declares, in its order and words: model, its options (effort, worktree, base branch...), permission and mode.
- **Task detail**: the session panel prints the chosen launch options (model and each option changed from its default) and, once the harness reports them, the branch and directory, marked "reported by" the harness.
- **Task detail** shows a **Usage** panel when the task's harness reports what its session used (Claude Code does): turns, input tokens with cache read and cache write, output tokens, working time, and cost only when the harness reports one. Counts are compact; hover for the exact number. It reads "so far" while the task runs ([Claude Code](/docs/guides/claude-code)).

Task states, actions and completion: [Tasks](/docs/concepts/tasks).

## Trees

- **Trees page**: Active trees (most pressing first) and Completed in the last 7 days, with a count strip by each tree's next step. Each tree shows its last activity and created date and expands to its members in level order. Closed and All add done, completed and archived trees.
- **Tree view**: a list in level order with each task's needs and time in its state, or a top-down graph of execution steps and which needs are met. A side panel shows the tree's day-grouped activity or, for a selected task, its needs, start mode, base and handoff.
- **Task detail** has a Tree panel with the same controls, or **Add to tree** (a new tree or an active one).

How trees work: [Trees](/docs/concepts/trees).

## Schedules

The Schedules page lists every schedule. Actions: run now, pause/resume, edit, delete (spawned tasks are kept). Schedules also show in the project panel, the Tasks Scheduled (next 24h) group and the Dashboard's In flight counts. Create one from the New task drawer's Start field ([Schedules](/docs/concepts/schedules)).

## Search and palette

`Ctrl K` finds Stage tasks and projects by title.

| Key | Does |
|---|---|
| `Enter` | open the task |
| `Ctrl Enter` | open its harness session |
| `Alt C` | copy its task (or tree) reference |

The palette also offers Sync now.

## Links and references

- Task and tree detail headers have **Copy link** (a self-describing markdown link, `[stage task #12: Title](…/tasks/12)` or `[stage tree #4: Title](…/trees/4)`, for prompts) and **URL** (the bare link).
- Task and tree rows on laptop-width screens show a link icon on hover or keyboard focus.
- Pasted Stage task and session links (any host) render as live chips (number or "session", title, state) in prompts, final replies and handoff text. Tree and unknown links stay plain links.

## Answering questions

Needs-input tasks and notifications open the source harness for questions and approvals. In the desktop app, T3 links open the T3 app, else T3 in the browser. OpenCode opens the configured web client; with a separate client configured, task detail also offers **Open on service** and **Copy session ID** ([Connections](/docs/reference/connections)). Claude Code has no link: task detail offers **Copy resume command**, and its needs-input alert reads "Claude Code needs input. Answer it in a terminal with the resume command." Task rows and notifications offer the same button, as does Codex ([Claude Code](/docs/guides/claude-code)).

A harness that lets Stage answer (Claude Code, for the sessions Stage starts) lists what its session waits on in a **Requests** panel under the needs-input alert, which then reads "Claude Code is waiting for your answer.": a permission prompt with its command, file or URL and the harness's choices (Allow, Always allow with the rule it saves, Deny with an optional reason), or questions with their options and Other, answered together with **Send**. A task row or inbox row with exactly one permission prompt shows it on one line with its first and last choice (Allow, Deny); a question or several requests show **Answer**, which opens the panel. An answer the harness already got shows "Already answered in Claude Code or expired". The harness's own client keeps working the whole time.

A harness that takes messages from Stage (Claude Code) adds a **Follow up** box under Last word once the session finishes: **Send** (Ctrl or Cmd + Enter) continues the same session and the task runs again. When the turn ended asking you something, the box leads as **Reply** under "Claude Code is waiting for your reply.". While the session works the box keeps your draft and Send waits; a session that can't take a message says why. The timeline records "Follow-up sent from Stage".

## Snippets

Reusable prompt text, global or per project. Type `/` in a task prompt or notes to pick one and insert it.

## New-task defaults

Each connection keeps its own new-task defaults in its Manage drawer (Settings > Connections):

- **Set as default** makes it the connection new tasks start on, from the form, the palette, quick add or an agent. The row shows a `default` chip. A project that is not available there opens on its first available harness, and the form says so.
- **Model pin**: pin a model and its options per connection. Unpinned, tasks start at the harness default.
- Interaction mode and permission always start at the harness default.

## Notifications

| Event | When |
|---|---|
| needs input | a task or session asks a question or an approval |
| failed | a run failed |
| ready | a manual tree task can start; the notification offers Start |
| done | a run finished |

Each event is toggleable in Settings > Notifications, with one filter for every device. Notifications cover tasks and supported external sessions (subagents excluded). Completing a task in Stage sends no notification.

- **Inbox and toasts**: every notification lands in an in-app inbox and a toast. A needs-input toast clears once the question is resolved.
- **Silent rows**: pre-existing external sessions waiting for input appear as silent current-state rows in the inbox when they have no recorded notification group. They add no unread event, push, toast or synthetic history. A recorded group replaces the silent row. Local Claude Code sessions waiting for input always appear this way and never notify; a row offers Open, Copy resume command or "Answer in Claude Code", and Track fills in Track session for you to confirm.
- **Browser**: Web Push from the installable PWA. The app icon badge counts what needs input. It needs a secure context, `http://localhost` or HTTPS ([HTTPS and push notifications](/docs/usage/server#https-and-push-notifications), [Phone](/docs/guides/phone)); Settings > Notifications says "needs https" otherwise. **Send test** checks the device.
- **Desktop app**: native OS notifications, also while the window is closed ([Desktop](/docs/usage/desktop)).

## Settings

Three tabs.

### General

- **User**: the current user, read-only. Stage has no sign-in: everything is attributed to one default user.
- **Theme**.
- **Info**: the running server's version, how it runs, start time, identity, socket or URL, the desktop app's state and Open Stage at login, and copy diagnostics.

### Connections

- **Machines**: every machine, the main machine first, with online or offline, last seen, its build (flagged when it differs from the main machine's) and its connections as rows. Rename a worker inline; remove one behind a confirm that says what happens to its worker, connections and tasks. **Add machine** creates a one-time pairing link (10 minutes) and the copyable `stage worker join <link>` command, counts down, and shows when the worker joins; closing it while waiting revokes the code ([Machines](/docs/concepts/machines)).
- **Connections**: per machine, **Add connection** lists the harnesses it can still connect. **Manage** opens a connection's drawer: T3 pairing (Pair with T3 or a pairing code), the T3 URL, Browser URL and optional admin token; the OpenCode connection (one click for the service on this machine, an `opencode pair` link for another, Advanced); the Codex connection (Connect, the command that fixes a problem, the Codex CLI path); the Claude Code connection (Connect, which Claude it uses, Check connection, Claude command); the New tasks panel (Set as default, model pin); and a **Capabilities** list of what the harness declares it can do (start tasks, stop from Stage, send follow-ups...), each available or unavailable with the harness's reason. A disconnected connection stays as a Disconnected row with Reconnect and Forget. Details: [Connections](/docs/reference/connections).
- **Diagnostics**: independent T3, OpenCode, Codex and Claude Code connection diagnostics.
- **Sync now**: a full sync also runs every 5 minutes.
- **Auto-complete**: a connection can complete a task for you. A successful run whose T3 thread is settled, whose OpenCode session or Codex thread is archived, or whose Claude Code session is removed (`claude rm`), is accepted automatically (provenance shown, once per run; changing the state back undoes it; failed or interrupted runs never). On by default; toggle it per connection.

No harness setting comes from the environment.

### Notifications

The per-event filter and this device's delivery: Enable, Send test, Disable (the desktop app adds System settings).

### Completion and recovery

- **User completion** is separate from execution. A task's State picker shows its status and the one manual change it allows. Picking Completed (or Review on a row) opens a review of cached evidence and dependent impact, with an optional acceptance note. Active work must stop first.
- **Change state**: moving a completed task back preserves accepted-result history and already claimed attempts, while blocking unclaimed dependents. Later harness activity never revokes acceptance. Agents report outcomes but have no completion or reopening tool.
- New trees default to auto start and tasks inherit; existing explicit policies remain.
- **Unconfirmed launches** reconcile automatically without creating a new attempt. For older launches without safe identity, use **Link existing session** on task detail: paste a session link, preview, then attach. Attachment launches no work.
