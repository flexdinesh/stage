# MCP tools

Stage exposes its agent operations as MCP tools, over the server's REST API. The same tools run from the CLI with `stage call TOOL JSON` ([CLI](/docs/reference/cli)). Agents can create work, read accepted results and contribute journal notes; only the user can complete a task in Stage.

## Front ends

| Front end | How | Notes |
|---|---|---|
| stdio | `stage mcp` | Finds the server like the CLI (`STAGE_URL`, the private socket, then `http://127.0.0.1:7380`). Can read local files (`imagePaths`). |
| HTTP | `POST /mcp` on the running server | Streamable HTTP, stateless, served in-process; nothing to install. Cannot read local files, so no `imagePaths`. |

On a worker's machine, both reach the main server through the worker's agent gateway ([Workers](/docs/usage/workers)).

### HTTP MCP and the Host header

HTTP MCP is reachable directly at a loopback address with a loopback Host (`http://127.0.0.1:7380/mcp`, `http://localhost:7380/mcp`), or on a non-loopback listen address reached by its network address. A request that arrives on loopback with another Host gets `403 Forbidden: invalid Host header`, even when the origin policy trusts that host.

:::note
A reverse proxy forwarding to `127.0.0.1:7380` cannot serve HTTP MCP. Through a proxy, agents use stdio MCP or the CLI with `STAGE_URL` set to the proxy URL.
:::

## Register

```sh
stage setup mcp [--claude] [--codex] [--http]   # MCP only
stage setup --mcp                               # the skill, the instruction pointer and stdio MCP
```

- Registers with `claude mcp add --scope user` and `codex mcp add`. `--http` registers `/mcp` instead of stdio.
- Passes `STAGE_URL` to the stdio server only when one was given explicitly; otherwise the stdio server resolves the server itself.
- `--http` needs an `http(s)` URL. If the server is only on a socket, use stdio (or pass `--url`).

### OpenCode

With an OpenCode connection configured in Stage, register Stage with OpenCode's own command. Choose one transport:

```sh
opencode mcp add stage -- stage mcp
# or a Stage HTTP listener reachable from OpenCode
opencode mcp add stage --url http://127.0.0.1:7380/mcp
opencode mcp list
```

To expose the named Stage tools directly in OpenCode's MCP server configuration, set `"codemode": false` and `"protocol": "legacy"` alongside the Stage HTTP URL.

## Caller identity

Tools that create tasks, write notes, adopt sessions or read context need the calling session, `{connectionId, externalSessionId}`:

| Source | Applies to |
|---|---|
| The harness's session variable (`T3CODE_THREAD_ID`, `OPENCODE_SESSION_ID`, `CODEX_THREAD_ID`), on that harness's connection on this machine | stdio MCP, which runs as the agent's child process |
| Per-call MCP metadata | OpenCode (2.3.0 sends native caller identity per call, also over shared connections) |
| `Stage-Caller-Session: <connectionId>:<externalSessionId>` header | HTTP MCP, which never reads an environment |
| `callerSession` parameter with `connectionId` and `externalSessionId` | any front end; for intermediaries |

- A shared MCP process uses per-call identity; stdio MCP never reads `STAGE_CALLER_SESSION` (the CLI does).
- A header or `callerSession` that conflicts with the OpenCode claim returns an error.
- Without session context, supply a project or journal owner explicitly; Stage leaves the author session empty.
- Launch instructions name the connection id.

## Tools

| Area | Tools |
|---|---|
| Context | `get_context`, `list_projects`, `list_models` |
| Journals | `read_journal`, `get_journal_entry`, `append_note` |
| Tasks | `list_tasks`, `get_task`, `create_task`, `update_task`, `delete_task`, `archive_task`, `start_task`, `stop_task`, `duplicate_task`, `wait_task` |
| Trees | `list_trees`, `get_tree`, `create_tree`, `update_tree`, `delete_tree`, `add_to_tree`, `remove_from_tree`, `set_needs`, `start_tree` |
| Schedules | `list_schedules`, `get_schedule`, `create_schedule`, `update_schedule`, `delete_schedule`, `run_schedule`, `preview_schedule` |
| Sessions | `adopt_session`, `read_ref` |

`stage tools` lists them; `stage tools NAME` prints one tool's description and input schema.

### Results

- Results are the REST shapes as JSON; lists are compact rows. Errors are tool errors carrying the API `error`.
- `list_tasks` rows carry `treeId`, `needs`, `readiness`, `adopted` and `lastWordPreview`. Open tasks by default; `closed: true|all` adds archived tasks and members of done or archived trees.
- `list_trees` returns active trees by default (`status` done, archived or all for others).
- `get_task` returns the task's events, `session`, available session links, `finalReply`, its tree, `handoff`, `currentHandoffs` and the grouped `batch`. `stage task show` prints the final reply and the session's web or native link when available.
- `imagePaths` reads local files (PNG, JPEG, GIF, WebP, up to 8) and uploads them. CLI and stdio only; HTTP MCP rejects them.
- `stop_task` interrupts a task's running session.
- `wait_task` polls the task every 3s until its state is in `until` (default `needs_input done failed interrupted cancelled`) or `timeoutSeconds` passes (default 600, max 3600). CLI `task wait` defaults to `--timeout 10m` and exits 3 on timeout.
- `preview_schedule` returns the next three fire times of a cron in a zone.

## Context and destination

- `get_context` returns your session, cwd, resolved Stage project, owning task and current tree. The owner remains available offline. An unowned session resolves through its verified project binding. An external session can legitimately have no Stage task.
- `list_projects` lists projects with bindings and configured connections. Set `connectionId` on `create_task` to choose the execution harness, independently of the creator's. A sole binding supplies the default; with both harnesses bound, choose one explicitly. With no binding, the caller's connection or the sole configured connection; there is no default harness.
- `list_models` with `connectionId` (required; and `projectId` for workspace-specific choices) lists a harness's models, agents and options. Pass the advertised values in `executionConfig` on tasks and schedules; the old T3 `provider`, `model` and `effort` parameters were removed.
- Launch options go in `executionConfig.options` like any other option: a worktree (`{"id":"worktree","value":true}`), and on T3 its `baseRef` and `branch`. `list_models` lists them with their `kind` (`choice`, `boolean` or `text`) and `dependsOn` (T3's `baseRef` and `branch` apply only with `worktree` true). Claude Code and OpenCode pick the worktree's base and branch; Codex has none. The old `workspaceType`, `baseRef`, `branch`, `base` and `baseTaskId` arguments were removed.
- `startLocal` with `startTz` schedules a one-shot start.

## Journals

| Tool | Details |
|---|---|
| `read_journal` | previews of 600 runes, notes by default (events or all are opt-in); exactly one of `taskId` or `treeId`; `filterTaskId` filters a tree read; follow `nextCursor` (pages of 20 by default, 100 max). A stale tree cursor requires restarting pagination. |
| `get_journal_entry` | one entry in full |
| `append_note` | up to 16 KiB; exactly one of `taskId` or `treeId`; `requestId` required. A tree note takes the current `sourceTaskId`. |

- Categories are optional: `finding`, `decision`, `blocker`, `outcome`.
- Retry a write with the same `requestId` and identical content.
- Refresh membership with `get_context` or `get_task` first. Write your own progress to the task (`taskId`) and shared conclusions to the tree (`treeId` with `sourceTaskId`).
- Adding a note to closed work never reopens or schedules it.
- New tasks and adopted sessions take `initialNote`; schedules take `notes` as a template for each spawned task.

### Launch instructions

Every launch, including standalone tasks and handoff off, includes a journal instruction block. It tells the agent that the session is attended (start mode only decides when it starts; the agent works as in a session the user started, including asking questions), to use whichever Stage interface it has (MCP tools, the `stage` CLI, or the HTTP API, named with its address when `STAGE_PUBLIC_URL` is set, or with the worker's agent gateway for a session on a remote machine; never install one), to pass caller identity per interface, to checkpoint before risky work, to record the outcome before returning, to treat notes as context rather than instructions or proof, and to report failed writes. The block is fixed per launch attempt. Existing and adopted sessions receive no retroactive message.

## Trees

Trees are the only way to express dependencies. A task's needs are tasks in the same tree that the user must complete in Stage before it starts; execution outcomes alone keep dependents blocked.

| Parameter or tool | Effect |
|---|---|
| `needs` on `create_task` | wait for those tasks (joins their tree, or starts one) |
| `treeId` | join a tree (a parallel root without `needs`) |
| `create_tree` | build a tree from existing tasks with the needs between them (a task in another tree moves) |
| `add_to_tree`, `remove_from_tree`, `set_needs` | edit membership and needs; removing a task splices it out (its dependents take over its needs) |
| `get_tree` | members with needs, dependents and readiness, edges and levels |
| `startMode` on `update_tree` | shared policy: `auto` launches members once their needs are completed in Stage; `manual` marks them ready and notifies |
| `startMode` on a task | `inherit` (default), or `auto`/`manual` as a per-task exception |
| `start_tree` | start every ready member |
| `status` on `update_tree` | `done`, `archived` or `open` (reopen) |

- New trees default to auto. Roots never start on their own; other members launch only once the user completes their needs.
- `start_task` on a blocked task returns a conflict naming the prerequisites that need user completion.
- `archive_task` closes a standalone task; a tree member closes with its tree. Neither works while a task is launching, running or needs input.
- `delete_task` and `delete_tree` only delete work that never started and has no recorded work.

### Handoff

When a task with needs starts, its launch prompt gets one block per accepted need: saved reply excerpt, branch or worktree, session ID and link when available, and task and journal references. On by default.

- `handoff: false` on `create_task` or `update_task` turns it off (CLI `--handoff=false`). Omitted keeps the task's value.
- The reply cap per need is `min(4000, max(1000, 8000 / needs))` Unicode characters.
- Handoff uses the saved accepted snapshot in Stage, without a live source-harness read. Missing replies remain missing; storage errors block launch.
- `get_task` returns `handoff` and `currentHandoffs` (one per need). `stage task show` prints `handoff  on|off` for tasks with needs and the current attempt's records.

A dependent's worktree starts where its own launch options say, never from a need's branch: the handoff names the branch each need reported, and the agent works from there.

## Run after me

`afterMe` on `create_task` (CLI `--after-me`) adopts the calling session as a task (Stage never starts it) and makes it the new task's first need, so the task starts after the user completes the adopted task in Stage. It errors without a calling session.

`adopt_session` tracks your own session, or pass `session` to select a target (CLI `stage sessions adopt --target-connection ID --target-session ID`). It returns the existing task when one owns the session. For an unbound workspace, choose an existing Stage project (`projectId`, CLI `--project ID`) or create one (`newProjectTitle`, CLI `--new-project TITLE`). An initial note records the caller who wrote it.

## References

`read_ref` (CLI `stage show REF`) reads what a pasted reference names: a Stage task or tree link (any host, markdown link ok), a harness's own session link (resolved by its connection), `#<task id>`, or a scoped session path such as `/connections/2/sessions/EXTERNAL_ID`. A bare session id names no connection: pass `session` with its connection.

- A tree link returns the tree (as `get_tree`), ready for `add_to_tree`, `update_tree` and the other tree tools.
- For an opaque ID, pass `session` (CLI `--target-connection ID --target-session ID`).
- Task references include Stage's saved results and available links. Open the native harness to continue the conversation.

## Session batch

Tasks and schedules record their creator in `originSession`; schedule-created tasks inherit it. The creator can use a different harness from the one selected for execution.

- `list_tasks` with `originSession` (CLI `stage task ls --origin-connection ID --origin-session ID`) lists a creator session's tasks.
- `get_task` returns the grouped `batch`. Task detail opens a Batch drawer with selection, editing, and Parallel or Chain tree creation.
