# Connections

Stage runs tasks on existing harness services, T3 Code and OpenCode V2, and on Claude Code and Codex on the computer Stage runs on. Each connection is set up in Settings > Connections or with `stage harness`. Credentials and addresses are stored in the server's database (on a worker, in that machine's credentials file), so a service or desktop app needs nothing else.

:::note
Harness settings are never environment variables. `T3_URL`, `T3_PUBLIC_URL`, `T3_ADMIN_TOKEN` and the `OPENCODE_*` variables are no longer read; a server logs a warning naming any still set ([Configuration](/docs/reference/configuration)).
:::

## First run

A new install has no connections. You can create projects and plan tasks before connecting a harness. While nothing is connected, the Dashboard shows a **Connect a harness** alert that links to Settings > Connections, which offers **Connect T3** and **Connect OpenCode**.

After connecting, Stage discovers eligible workspaces and imports them into projects. You can also bind existing workspaces yourself. On a connection with several workspaces for a project, Stage uses the primary unless the task specifies a binding. Stage owns project titles and archive state. Missing workspaces preserve their projects and history. See [Projects](/docs/concepts/projects).

## CLI

```sh
stage harness                        # harnesses this server knows, its machine profile, which can run here
stage harness KIND [status]          # KIND's connection: state, settings, actions
stage harness KIND set FIELD=VALUE   # save settings; --reset FIELD restores a default
stage harness KIND run ACTION [FIELD=VALUE...]
stage harness KIND disconnect        # forget KIND's credentials (tasks stay)
```

`KIND` is `t3`, `opencode`, `claude` or `codex`.

## T3 Code

Stage connects to one T3 Code server through T3's MCP endpoint and OAuth. It needs a T3 session token, which it gets by pairing. T3 counts as connected only once paired; until then Stage never contacts it in the background.

### Pair

| Method | When | How |
|---|---|---|
| **Pair with T3** (one click) | T3 runs on the same machine as the Stage server (the T3 URL is `localhost` or a loopback IP) and its `t3` CLI is found | Stage runs `t3 auth pairing create` with a 5 minute code and redeems it. |
| **Pairing code** | T3 runs on another machine, or its CLI is missing | Run `t3 pair` on the T3 host and paste the code into the Dashboard alert or Settings (Pair). |

```sh
stage harness t3 run auto-pair         # auto-pair through the t3 CLI on the server's machine
stage harness t3 run pair code=CODE    # redeem a code from `t3 pair` on the T3 host
```

The `t3` CLI is looked up on `PATH`, then in `~/.local/bin`, `~/.bun/bin`, `~/.local/share/pnpm`, `~/.npm-global/bin`, `~/.volta/bin`, `/usr/local/bin` and `/opt/homebrew/bin`. Set `T3_BIN` when it is elsewhere (a service manager's `PATH` is minimal).

Pairing starts a full sync.

### Address

Set both in Settings > Connections > T3 (Manage) or with `stage harness t3 set`.

| Setting | Field | Default | Purpose |
|---|---|---|---|
| T3 URL | `url` | `http://127.0.0.1:3773` | The T3 server Stage calls. Under Docker compose, T3 on the host is `http://host.docker.internal:3773` (T3 must listen beyond loopback). |
| Browser URL | `publicUrl` | the T3 URL | The T3 address browsers use for Open in T3 links. Set it when browsers reach T3 at another address. |

```sh
stage harness t3                              # show it
stage harness t3 set url=http://10.0.0.5:3773 # save it (http(s)://host[:port])
stage harness t3 set --reset url              # back to the default
```

Once the server is bound, the T3 URL can only change to an address serving the same T3 environment.

### Admin token

Optional. A pairing gives Stage a 30-day session that is not renewed. With a T3 admin token, Stage mints and renews its own session instead, renewing when less than 5 days remain. Issue one on the T3 host:

```sh
t3 auth session issue --ttl 3650d --label stage --scope access:write --scope orchestration:read --scope orchestration:operate --scope settings:write --scope source-control:write --token-only
```

Paste it as **Admin token** in Settings > Connections > T3 (Manage), or run `stage harness t3 set adminToken=TOKEN`. Stage stores it and never shows it again. On a worker it stays in that machine's credentials file, like the T3 token.

### Disconnect and switch

- **Disconnect** forgets the token, the T3 URL, the Browser URL and the admin token and stops syncing. Tasks and bindings stay; pairing the same T3 again resumes it.
- A disconnected connection stays in Settings as a **Disconnected** row with what remains on it, **Reconnect** (opens its setup) and **Remove connection**. Removing it clears its workspace bindings and keeps its task history read-only. Pairing again creates a new connection. Retired connections appear under **Previous connections**, with their machine name and usage. Their bindings are hidden from project pickers and workspace lists even before removal.
- **Switch to another T3**: Disconnect, set the T3 URL, and pair the other T3. Tasks from the first T3 stay as read-only history, and discovery resolves the new T3's workspaces from available evidence. Pairing the first T3 again restores its tasks and bindings.
- A disconnected T3 whose environment is paired again on another machine moves onto that connection automatically at the next sync.

### Status and troubleshooting

```sh
stage harness t3 status    # URL, reachability, pairing, token expiry, sync, auto-pair availability
```

- Trouble (T3 unreachable, unpaired, session expired or rejected) shows as an alert at the top of the Dashboard with the fix, and in the connection status row ([The app](/docs/reference/app)).
- Settings shows the T3 connection, Pair, the T3 URL, the Browser URL, the admin token and Sync now. A full sync also runs every 5 minutes.
- Stage reports itself and T3 separately: a missing or offline T3 never stops the Stage server from starting, and `stage service status` lists T3 apart from the server's own health.

## OpenCode V2

Stage connects to an existing OpenCode V2 service over its HTTP API. Tested with 2.3.0; any version whose API has the operations Stage uses works.

### Connect

| Method | When | How |
|---|---|---|
| **Connect** | OpenCode runs on the Stage server's machine | Click **Connect**, or `stage harness opencode run connect-local`. Stage reads the service's registration file (`$XDG_STATE_HOME/opencode/service.json`, else `~/.local/state/opencode/service.json`, also on macOS) and signs in as `opencode` with its password, which is never stored. Each health check re-reads the file. |
| **Pairing link** | OpenCode runs on another machine | Run `opencode pair` there and paste the link, or `stage harness opencode run pair link=LINK`. The link is redeemed once for a 30-day session that Stage renews automatically after 7 days. |
| **Advanced** | anything else | A plain service address, with optional HTTP Basic username and password. |

Connecting a different OpenCode service needs confirmation (`newInstance=true` on the CLI); the current connection retires.

A password change on the OpenCode host revokes a paired session: pair again.

### Browser and web client

| Setting | Field | Purpose |
|---|---|---|
| Server URL | `endpoint` | The OpenCode service Stage calls |
| Browser URL | `browserEndpoint` | The service address browsers use, when your phone or browser reaches it at another address |
| Web client URL | `webClient` | A separate OpenCode web client. Register the service in that browser once; Settings explains how on a fresh device. |

With a separate web client configured, task detail also offers **Open on service** and **Copy session ID**.

### Disconnect

`stage harness opencode disconnect`, or Disconnect in Settings, forgets the address and credentials. Tasks and history stay. The row stays as Disconnected, like T3.

A disconnected OpenCode leaves planning and the other harness available.

## Claude Code

Stage runs tasks as Claude Code background sessions (`claude --bg`) on a computer: where Stage runs (the desktop app, or `stage serve --local-harnesses`), or on a [worker](/docs/usage/workers) (the worker service, or `stage worker run --local-harnesses`). Not in Docker. Stage uses that computer's Claude login and stores no Claude credentials.

### Connect

Click **Connect**, or `stage harness claude run connect`. Stage checks the `claude` command (`claude --version`) and that Claude is logged in (`claude auth status`); the connection is named by Claude's config folder (`Claude Code (~/.claude)`). Stage finds `claude` on its `PATH`, then in `~/.local/bin` and the other usual install folders; set **Claude command** (`stage harness claude set binary=/path/to/claude`) for anything else.

| Status | What to do |
| --- | --- |
| `not_found` | Install Claude Code, or set the Claude command |
| `logged_out` | Run `claude auth login` in a terminal, then connect again |
| `error` | The command did not answer within 20 seconds, or Claude now uses another config folder: check the command and connect again |

In Settings, the Claude Code row shows its config folder and version (`~/.claude · 2.1.332`), or why it is not connected. **Manage** opens its card: **Connect** while not connected; the reason and **Connect again** on a problem (plus `claude auth login` to copy when logged out); once connected, the command Stage runs, the version, the config folder, the login, whether sessions keep running when Stage restarts and **Updates** (instant through Claude hooks for sessions Stage starts, else every few seconds with the reason), with **Check connection** and **Disconnect**. **Claude command** and its **Save** are at the bottom.

`stage harness claude` prints the same:

```text
claude connected (Claude Code 2.1.332)
  command  /home/me/.local/bin/claude (default lookup)
  config   /home/me/.claude
  login    logged in
  scope    own systemd scope (Claude's daemon outlives a Stage restart)
```

On a problem it adds the error and the next steps: `claude auth login`, then `stage harness claude run connect` when logged out; `stage harness claude set binary=PATH` when the command is not found; `stage harness claude run connect` when disconnected.

### Running tasks

Each task starts one background session in the project folder or in a new Claude worktree with the Claude Code worktree option on (Claude branches it from origin's default branch and names it). Pick Claude's default model or opus, sonnet, haiku or fable, an effort and a permission mode. Claude must trust a folder before it runs there: run `claude` in it once and accept the prompt. Otherwise the task returns to backlog saying so. Prompt images are written under Stage's data dir (`claude/images`; a worker's own), never into the project folder, and listed in the prompt for Claude to open; the launch's settings let Claude read that folder without asking, and a launch with images removes those older than 30 days. Stage removes the `.claude/stage-images` folders earlier versions wrote in projects.

When a session waits for you, answer in Claude: task detail, task rows and notifications offer **Copy resume command** (`claude attach <id>`, or `claude --resume` once the session is gone from `claude agents`). For a session on a worker it reads **Copy resume command for** the machine: run it there. Projects come from the folders Claude knows; Git checkouts import as Stage projects. **Track session** takes a session UUID, the 8-character ID `claude agents` shows, or a pasted `claude attach` or `--resume` command. A session T3 started is refused: "This Claude session was started by T3. Track it through T3."

Removing a finished session with `claude rm` completes its done task (**Complete tasks when removed in Claude Code**, on by default). Claude ending an idle session after about an hour does not, and neither does removing one mid-turn or one waiting for you.

### Disconnect

`stage harness claude disconnect`, or Disconnect in Settings. Stage stops using Claude Code; sessions keep running in Claude, tasks and history stay, and connecting again resumes the same connection.

## Codex

Stage talks to the Codex app-server daemon on the machine Codex runs on: where Stage runs on your computer (the desktop app or Stage's per-user service, or `stage serve --local-harnesses`), or a [worker](/docs/usage/workers) with local harnesses (the worker service, or `stage worker run --local-harnesses`). It is unavailable in the Docker image. Stage stores no Codex credentials; log in with `codex login`.

### Connect

Click **Connect**, or `stage harness codex run connect`. Stage starts the daemon when it is down (at most once every 30 seconds), reads the Codex login and connects the Codex home. It never stops, restarts or updates the daemon, which keeps running turns across Stage restarts and serves `codex resume` and Codex Desktop.

| Setting | Field | Purpose |
|---|---|---|
| Codex CLI | `binary` | Path to the codex binary. Empty uses `codex` on PATH (`stage harness codex set binary=PATH`). |

| State | Meaning |
|---|---|
| connected | Stage reaches the daemon and Codex is signed in |
| not connected | Codex is not connected on this machine |
| signed out | the daemon answers but Codex has no login: run `codex login` |
| unreachable | the daemon is down or not answering |
| not installed | the Codex CLI is missing |

When not connected, Settings shows the reason and the command that fixes it.

### Tasks

Tasks run in the project root: no Codex worktrees, no Plan mode. Images are sent with the prompt. Permission: **Read only**, **Auto** (default) or **Full access**. Workspaces are the projects Codex trusts; trust a project in Codex, Stage never edits Codex's config.

Answer questions and approvals in Codex: **Copy resume command** on a task row or task detail copies `cd <dir> && codex resume <id>`. Track session takes a thread id or a `codex resume <id>` command; threads T3 Code started are refused (track them through T3).

### Disconnect

`stage harness codex disconnect`, or Disconnect in Settings, stops tracking. Tasks and history stay; the daemon and its threads stay in Codex.

## Connections on workers

On a main server with workers, each machine has its own connections. Settings > Connections groups them by machine; a remote machine's setup runs on that machine through its worker, and its credentials stay there ([Workers](/docs/usage/workers)).
