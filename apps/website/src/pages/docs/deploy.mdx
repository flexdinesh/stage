# Headless server

On a headless install (or any machine where you want stage without the desktop app), the `stage` CLI runs the server. One server owns one data dir. To run it on another host (a VM, a home server, a cluster) while harnesses run on your own machines, see [Main server and workers](#main-server-and-workers). Install first: [Install](/docs/install) with `--headless`.

## Run as a service

The usual way: an OS per-user service (systemd user unit on Linux, launchd agent on macOS) supervises `stage serve --managed`. It runs as you, never root, restarts on failure with backoff, and logs to journald (Linux) or `~/Library/Logs/stage/stage.log` (macOS). The desktop app starts this same service itself.

:::steps

### Start

```sh
stage service start      # register and start; waits until the server answers
```

It creates `service.env` if missing and never restarts a running server.

### Pair with T3

Open the Dashboard ([Listeners](#listeners) for browser access) or run `stage harness t3 run auto-pair`. See [Connect to T3](/docs/t3).

### Optional: start at login

```sh
stage service enable     # login startup, separate from running now
```

:::

| Command | Does |
|---|---|
| `stage service start [--wait 30s]` | register or update the definition, create `service.env`, start if not running, wait for readiness |
| `stage service restart` | start, and restart a running server (apply `service.env` edits) |
| `stage service stop` | stop through the service manager; the server drains for up to 100s |
| `stage service status` | state, Stage health and T3 reported separately, log location, problems with fixes |
| `stage service logs [-f] [-n 100]` | recent log lines |
| `stage service enable` / `disable` | login startup on or off (neither starts nor stops it) |
| `stage service uninstall` | stop, disable and remove the definition; keeps data, `service.env` and logs |

Every command but `logs` takes `--json`. Service commands always act on this installation's own service; `--url` and `STAGE_URL` do not apply. Agent commands never start a server; when nothing answers, their error suggests `stage service start`.

- **Config**: the service reads only `service.env`, never your shell: `~/.config/stage/service.env` (`$XDG_CONFIG_HOME/stage/`) on Linux, `~/Library/Application Support/stage/service.env` on macOS. See [Configuration](#configuration).
- **Logout**: on Linux the user manager stops at your last logout unless lingering is on (`loginctl enable-linger`); with lingering an enabled service also starts at boot. stage never changes lingering. On macOS the agent runs in your GUI session. Without a user manager (no logind session, containers, WSL without systemd) `stage service` exits 6 with remedies; run `stage serve` in the foreground or under your own supervisor instead.

## Run in the foreground

```sh
stage serve                                    # or just `stage`; listens on 127.0.0.1:7380
stage serve --listen unix,127.0.0.1:7380       # the private socket and TCP, one process
```

A foreground server reads its config from the environment only (no `.env` file). It stops with its terminal (SIGINT/SIGTERM drain in-flight requests for up to 100s). Only one server can own a data dir: a second one, or a foreground server against the running service, exits with the holder's pid and listeners (run `stage service stop` first).

`stage status [--wait DUR]` shows which server the CLI reaches, its version, readiness and T3 state.

## Listeners

One process serves every listener. `STAGE_LISTEN` takes a comma list; `stage serve --listen` (repeatable) replaces it.

| Item | Meaning |
|---|---|
| `host:port` | TCP. An empty host means all interfaces. |
| `unix` | the private default socket for this data dir, mode `0600` (e.g. `/run/user/1000/stage/stage.sock`) |
| `unix:/abs/path.sock` | an explicit socket, mode `0660` (a proxy in its group can reach it) |

- Foreground default: `127.0.0.1:7380`. Service default: `unix` only. The service requires `unix` (the socket the desktop and CLI use); add TCP for a browser with `STAGE_LISTEN=unix,127.0.0.1:7380` in `service.env`, then `stage service restart`.
- The CLI and `stage mcp` find the private socket by themselves when a server owns it; otherwise they use `http://127.0.0.1:7380`. `STAGE_URL` (or `--url`) overrides it: an `http(s)` URL or `unix:///abs/path.sock`.
- Browsers need TCP, or a reverse proxy in front of a socket (e.g. Caddy `reverse_proxy unix//run/stage/stage.sock`).
- Socket paths must be absolute and fit the OS limit (107 bytes on Linux, 103 on macOS).

## Configuration

Environment variables: `service.env` for the service (a `KEY=VALUE` file, mode `0600`; apply edits with `stage service restart`), the shell for a foreground `stage serve`.

| Variable | Default | Purpose |
|---|---|---|
| `STAGE_LISTEN` | foreground `127.0.0.1:7380`; service `unix` | listen addresses ([Listeners](#listeners)) |
| `STAGE_PUBLIC_URL` | unset | HTTPS URL the PWA is served at. Its origin is trusted by the [request origin policy](#security); when `https` it is the Web Push VAPID subject (a fallback is used otherwise). Push works without it. |
| `STAGE_ALLOWED_ORIGINS` | unset | comma list of extra trusted browser origins (`https://host[:port]`), e.g. a Tailscale or Caddy hostname other than `STAGE_PUBLIC_URL`'s |
| `T3_BIN` | unset | the `t3` CLI that Pair with T3 runs, when it is not on `PATH` or in a usual install dir |
| `STAGE_DATA_DIR` | see [Data](#data) | data dir for a foreground server. Not allowed in `service.env`: the service always uses the default. |

Harness connections (T3 and OpenCode addresses, tokens and passwords) are set in Settings > Connections, never in the environment ([T3 address](/docs/t3#t3-address)). `T3_URL`, `T3_PUBLIC_URL`, `T3_ADMIN_TOKEN` and the `OPENCODE_*` variables are no longer read: a server logs a warning naming any still set, and in `service.env` they are errors.

In `service.env`, unknown keys, `STAGE_DATA_DIR`, or a file readable by group or others make `stage service start` fail (exit 7) instead of a restart loop.

## Data

The SQLite database (`stage.db`) lives in the data dir: `$XDG_DATA_HOME/stage`, else `~/.local/share/stage` (macOS: `~/Library/Application Support/stage`). Back it up.

Before migrating an existing database (after an update), the server copies it to `<data dir>/backups/stage-schema<N>-<time>.db`, keeping the newest 3. A server refuses to start on a database newer than it knows, so an older binary never runs against a migrated database. Uninstalling keeps the data dir.

## Security

:::warning
stage has no authentication. Anyone who can reach a listener can read tasks and journals, stop tasks, and launch agents in full-access mode on the host (`full-access` is the task default).
:::

- It binds `127.0.0.1` by default (the service: a private socket only). This keeps other machines out, not browsers.
- `/api` and `/mcp` reject requests browsers send on behalf of other sites: a Host other than an IP, `localhost` or a trusted origin's host (DNS rebinding), cross-site and same-site requests (`Sec-Fetch-Site`, `Origin`), and form-encodable bodies (`text/plain`, urlencoded). Trusted origins are `STAGE_PUBLIC_URL`'s and those in `STAGE_ALLOWED_ORIGINS`; any other hostname gets `403 host … not allowed`.
- That policy is not authentication. Any process or person that can reach a listener directly has full access. A private socket (`unix`, mode `0600`) limits that to your user.
- Before exposing stage to a network, put an authenticating HTTPS reverse proxy in front and keep stage itself unreachable except through it. A tailnet limits who can connect, not what they can do.
- The one exception is `/api/worker/*`: workers authenticate there themselves, with a one-time pairing code and then a revocable machine token. Your proxy passes that prefix through without user auth ([Auth proxy](#auth-proxy)).

## HTTPS and push notifications

Push notifications and installing the PWA need a secure context. `http://localhost` is one, so both work in a browser on the same machine with no setup. Other devices (phone, laptop) need HTTPS with a certificate they trust. Settings > Notifications says "needs https" when a page is opened over plain HTTP from another address.

The server only makes outbound requests to the browser push services (Apple, Google, Mozilla), so the URL can stay private (LAN or tailnet). Devices need internet to receive pushes.

Options, easiest first:

- **Tailscale serve**: a real certificate for your tailnet name, nothing to install on devices; easiest for iOS. Enable HTTPS certificates for the tailnet, then on the stage host (with a TCP listener on `127.0.0.1:7380`):

  ```sh
  tailscale serve --bg http://127.0.0.1:7380
  ```

  stage is then at `https://<machine>.<tailnet>.ts.net`, reachable only from your tailnet. Add that origin to `STAGE_ALLOWED_ORIGINS` (or set it as `STAGE_PUBLIC_URL`).

- **Caddy**: with a real domain, Caddy gets a certificate automatically:

  ```txt
  stage.example.com {
      reverse_proxy 127.0.0.1:7380
  }
  ```

  For a LAN-only name, issue a certificate with [mkcert](https://github.com/FiloSottile/mkcert) (`mkcert stage.lan`) and use `tls stage.lan.pem stage.lan-key.pem`. Every device must trust the mkcert root CA; on iOS install it as a profile, then enable it under Settings > General > About > Certificate Trust Settings.

- **Any reverse proxy** that terminates TLS and forwards to stage, with the streaming settings below.

Behind a proxy that forwards to `127.0.0.1`, HTTP MCP (`/mcp`) returns 403; agents use stdio MCP or the CLI with `STAGE_URL` set to the proxy URL ([Agents](/docs/agents)).

### Reverse proxy and SSE

The notifications inbox uses a Server-Sent Events stream (`/api/notifications/stream`).

- Caddy's `reverse_proxy` flushes it immediately. If your config uses `encode`, exclude that path so events are not buffered.
- Other proxies: disable response buffering (the server sends `X-Accel-Buffering: no`) and allow long-lived responses (a ping every 15s).

## Install as an app (PWA) and notifications

- **iOS/iPadOS 16.4+**: open the HTTPS URL in Safari, Share > Add to Home Screen, open stage from the Home Screen, then Settings > Notifications > Enable.
- **macOS**: Safari > File > Add to Dock (or use the site in Safari or Chrome), then Settings > Notifications > Enable.
- Settings > Notifications > Send test checks the device.

Which events notify (needs input, failed, ready, done, settled) is a global filter in Settings that applies to every device. See [Notifications](/docs/features#notifications). On the desktop app, notifications are native instead ([Desktop app](/docs/desktop#notifications)).

## Main server and workers

By default one stage install is one machine: the server runs your harnesses on the machine it runs on. You can also run one **main server** on a host every device can reach (a VM, a home server, a Kubernetes cluster) and join your laptops and desktops to it as **workers**. The main server keeps the database, the backlog, journals, scheduling, the UI, `/api` and `/mcp`. A worker has no database: it runs that machine's T3 and OpenCode connections, keeps their credentials, and does the machine-local work (Git checkouts, workspace matching). Settings > Machines lists every machine.

A worker always dials out to the main server, so laptops need no open ports and can sleep or change networks. An offline worker is an offline harness: its tasks keep their state, and launches wait until it is back.

### Main server

- Run it as a [service](#run-as-a-service), with [Docker](https://github.com/flexdinesh/stage/blob/main/compose.yaml), or on [Kubernetes](#kubernetes), behind HTTPS.
- Set `STAGE_PUBLIC_URL` to the HTTPS URL users and workers reach. Pairing needs it: links are built from it and workers dial it.
- One server per data dir, on a local disk. The Docker image never runs harnesses as local processes; T3 and OpenCode on your workers do the work.
- Workers and the main server need the same API version: update them together (`stage update` on each machine, and the main server's image).

### Auth proxy

stage has no user sign-in, so a main server on a network sits behind an authenticating HTTPS reverse proxy ([Security](#security)). Configure it to:

- Require user authentication for everything (the UI, `/api`, `/mcp`), including creating pairing links.
- Pass `/api/worker/*` through **without** user authentication, forwarding the `Authorization` header unchanged. Workers use it to join, for their channel, and for the [agent gateway](#agent-gateway). The pairing code or machine token is the authentication there; every other route refuses machine tokens.
- Keep the request's Host header (or rewrite it to an IP address or a host in `STAGE_ALLOWED_ORIGINS`). Workers send no `Origin`, so any other hostname gets 403.
- Not buffer responses and keep idle connections open past 15s: the worker channel is a long-lived Server-Sent Events stream with a keepalive every 15s ([Reverse proxy and SSE](#reverse-proxy-and-sse)).
- Accept request bodies up to 32 MiB: one message from a worker can be that large.

### Workers

On each machine that runs harnesses, install stage with `--headless` ([Install](/docs/install)), then:

:::steps

#### Pair

In Settings > Machines, click **Add machine** (or run `stage machine pair [--label NAME]` where the CLI reaches the main server, such as its host). It shows a one-time link, valid for 10 minutes, and the command to run.

#### Join

```sh
stage worker join 'https://stage.example.com/join#…'   # redeem the link; --label names the machine
```

This saves the main server's URL and a revocable machine token (`worker.json`, mode `0600`) in the worker dir. A plain `http://` link works for a LAN or loopback main server.

#### Start the worker service

```sh
stage worker service start     # the per-user worker service; waits until it runs
stage worker service enable    # optional: start at login
```

Settings > Machines shows the machine online within seconds.

#### Set up harnesses

Click the machine's **Harnesses** link (or **Set up harnesses** after it joins): the same T3, OpenCode and connection panels as this server's Settings, run on that machine through its worker. Credentials stay on the machine (`credentials.json`, `0600`, next to `worker.json`); the main server keeps only the connection and its status.

:::

| Command | Does |
|---|---|
| `stage worker join <link> [--label L]` | redeem a pairing link; refuses when already joined |
| `stage worker run [--listen ADDR]` | the worker in the foreground (instead of the service) |
| `stage worker status` | config, the main server's view of this machine, the running process and its gateway addresses |
| `stage worker leave [--local]` | remove this machine on the main server, then delete the local config; `--local` deletes only locally |
| `stage worker service start\|stop\|restart\|status\|logs\|enable\|disable\|uninstall` | the worker service, like `stage service` |

- **Config**: the worker service reads only `worker.env` next to `service.env` (`~/.config/stage/worker.env` on Linux, `~/Library/Application Support/stage/worker.env` on macOS), never your shell. It takes `STAGE_WORKER_LISTEN` ([Agent gateway](#agent-gateway)) and `T3_BIN`; the machine's T3 and OpenCode connections are set in Settings > Connections. A foreground `stage worker run` reads its shell.
- **One role per install**: a machine runs either this install's server or its worker, not both. The desktop app switches roles for you: **Join as worker** turns its server off (data kept) until you leave ([Desktop](/docs/desktop#this-machine-as-a-worker)).
- **Remove**: removing a machine in Settings > Machines revokes its token at once; its worker stops, and `stage worker status` says it was revoked. Its connections become history; its tasks stay.
- `stage update` restarts a running worker service and rolls back if the new one does not start.

### Agent gateway

Agents on a worker's machine use stage as usual: the `stage` CLI, `stage mcp` and HTTP MCP ([Agents](/docs/agents)). The worker serves a local gateway that forwards `/api` and `/mcp` to the main server with its machine token, so agents need no credentials or proxy access. Launch instructions for sessions on that machine name the gateway. The main server records which machine each agent write came from.

- By default it listens on this install's private socket, which the CLI and `stage mcp` find by themselves.
- For HTTP MCP clients, add a loopback TCP address in `worker.env`, then `stage worker service restart`:

  ```sh
  STAGE_WORKER_LISTEN=unix,127.0.0.1:7381
  ```

  Avoid a wildcard host: anything that reaches the gateway has agent access to the main server.
- The gateway cannot manage machines or change any machine's harness setup (403). If the main server is unreachable it answers 502.

### Kubernetes

A minimal example lives in [`examples/kubernetes`](https://github.com/flexdinesh/stage/tree/main/examples/kubernetes): a Deployment, a ClusterIP Service and a PersistentVolumeClaim for `stage.db`. There is no published image: build one from the repository `Dockerfile` at the release your workers run and push it to your registry. Then set the image and `STAGE_PUBLIC_URL`, apply the files, and put your [auth proxy](#auth-proxy) or ingress in front of the Service.

- **Exactly one replica**, with `strategy: Recreate`. One server owns one data dir through a file lock, and SQLite has one writer; a second pod on the volume exits at startup. Do not autoscale it.
- **A local volume**, never NFS: use a block-backed storage class (a cloud disk, local-path, Longhorn, Ceph RBD), `ReadWriteOnce`. File locks and SQLite locking are unreliable on network filesystems.
- **Graceful stop**: `terminationGracePeriodSeconds: 120` covers the server's 100s drain.
- **Probes** on `/api/health`, which answers 200 while the server and its database work, whatever harnesses or workers do.
- **Back up** the volume. Before a migration the server also copies `stage.db` into `backups/` on it.

## Update

```sh
stage update
```

Installs the latest release in the same mode and restarts the service if it was running this install (in-flight requests drain for up to 100s; no task is relaunched; T3 and its agents are untouched). A foreground `stage serve` is left alone, with a note to restart it. Details: [Install](/docs/install#update).
