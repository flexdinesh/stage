# Features

## Projects

Create a Stage project with just a title, even offline. Stage owns its title and archive state. Bind a workspace for each harness you use. Match can verify a shared checkout through explicit path mappings. Confirm a remote-only suggestion or choose the workspace manually. Changed paths need confirmation. Rebinding affects future launches; existing attempts and history stay attached to their original workspace. Sort by name or recent activity.

## Tasks

- **Task config**: prompt, harness, supported model and workspace options, and an optional initial journal note. Save to backlog or start right away.
- **Screenshots**: drop images on the prompt (or Add image; PNG, JPEG, GIF, WebP, up to 8 × 10 MB). They are sent to the T3 thread with the prompt on every launch.
- **Live status**: backlog, Launch unconfirmed, running, needs input, done, failed, interrupted or cancelled. Connection loss preserves execution state. User completion in Stage is separate.
- **Task actions**: start, stop, duplicate, archive, open in the selected harness. Delete is only for a task that never started and has no recorded work; archive recorded work instead.

## Trees and handoff

- **Trees**: group tasks into a tree, a DAG that can span projects, where a task needs other members. A task becomes eligible when the user completes every need in Stage. Blocked tasks cannot start early.
- **Start mode**: per tree, auto (launches a task once its needs are completed in Stage) or manual (marks it ready and notifies). Tasks inherit the tree's mode by default; a task can override it. Manual tasks whose needs are completed in Stage, and backlog roots, read ready: they list in the Dashboard and Tasks Ready groups and a `ready` notification offers Start.
- **Editing**: removing a task splices it out (its dependents take over its needs). Mark a tree done when you will not work on the rest (members keep their states, nothing more starts), or archive it; Reopen or Unarchive undoes it, and member activity leaves it closed until explicitly reopened. Done and archived trees and their tasks leave the Dashboard. Dissolve detaches the tasks and archives the tree; emptying a tree also archives it. Deleting a tree deletes its tasks and is only for work that never started and has no recorded work.
- **Track as task**: task detail can adopt an existing top-level session from either harness as a task, so it can be a tree node. stage never starts it; its prompt is read from the harness.
- **Views**: Trees lists trees (Active trees most pressing first, Completed in the last 7 days, a count strip by each tree's next step; expand one to see its members in level order, each tree with its last activity and created date; Closed and All add done, completed and archived trees), and each tree task in Tasks links its tree; the tree view (a list in level order with each task's needs and time in its state, or a top-down graph of execution steps and which needs are met), with a side panel for the tree's day-grouped activity or, for a selected task, its needs, start mode, base and handoff. Task detail has a Tree panel with the same controls, or Add to tree (a new tree or an active one). In a session's Batch drawer, check independent backlog tasks and pick New tree from n (Parallel, or Chain in check order).
- **Handoff** (on by default, per task): when a task with needs starts, stage appends one block per accepted need (cached reply excerpt, available artifact links, branch/worktree, task/journal and execution references) to the prompt, so work carries context forward. Task detail shows what was appended. Snapshots stay readable with the source harness offline. Missing replies remain explicitly missing.
- **Stacked T3 work on the same harness** (opt-in): a task's Workspace can be "#12's branch". Its worktree starts from a need's branch (the sole need, or the picked one), so it builds on unmerged changes. Unavailable predecessor branches block launch. Choose the configured base explicitly to continue.
- **Session batch**: task detail lists the tasks a session created ("Batch drawer", grouped by tree, then independent tasks); task detail shows it as a compact Batch panel.

## Journals

Every task and tree has an append-only journal of notes and events.

- Notes have optional categories (finding, decision, blocker, outcome), immutable IDs and provenance. Filter by notes, events or all, search text, page through entries, and open any entry in full.
- A tree's journal combines its own notes and events with the notes of its current members. Moving a task moves its notes; tree notes and events stay in their original tree.
- Adding a note to closed work never reopens or schedules it. Recorded work (notes or execution) protects tasks and trees from deletion.
- New tasks and adopted sessions accept an initial note; a schedule keeps a note template for each task it spawns; duplicates copy no notes.
- Agents read and write journals through the CLI and MCP, and every launch tells them how ([Journals](/docs/agents#journals)).

## Scheduled tasks

In the New task drawer pick Start:

- **At time** (one-shot): a backlog task starts at that wall time in a chosen zone. A time missed while the server was down starts late.
- **Repeat** (a schedule): presets Hourly / Daily / Weekdays / Weekly or a raw 5-field cron, in its own IANA zone. Each fire spawns and starts a new task with the schedule's config and images. A fire is skipped while the previous run is still pending, running or needs input; fires missed while the server was down are skipped.

Schedules show on the Schedules page, the project panel, a Scheduled (next 24h) group in Tasks and the Dashboard's In flight counts. Actions: run now, pause/resume, edit, delete (spawned tasks are kept).

## Sessions and transcript

Track an existing harness session from Stage, a project, or a tree. Choose the harness and paste its session link or ID, preview its title/project/state, then confirm. Optional title and initial note apply to newly tracked tasks.

Task detail keeps the opening prompt, cached final reply (up to 4000 characters), journal and historical artifact links. Open the source harness for conversations and detailed runs. There is no global session/history browser or automatic PR tracking. Historical data remains stored.

## Navigation and project scope

A sidebar (on a phone, a project chip in the top bar and bottom tabs) holds Dashboard, Tasks, Trees and Schedules and your projects. Pick a project to scope all four to it; the choice is remembered on each device. Projects with open work are listed by recent activity with their counts (needs input, waiting on you, running); pin the ones you want on top, and the rest fold away as quiet projects.

On a laptop, a bar over every page holds back and forward arrows and where you are (project, tree, task); right-click or long-press an arrow to jump further back through recent pages. On a phone, Back sits in the top bar on any page off the tabs. The desktop app also takes `Cmd+[`/`Cmd+]` (`Alt+Left`/`Alt+Right` on Linux) and the mouse side buttons.

The sidebar's last row sums up your connections: "All connected", the one thing that needs you, or how many do. Click it for each harness's state. On a phone the same list is on More, and the More tab shows a square while something needs attention.

## Dashboard

What needs you: needs input, finished runs awaiting your completion, ready tasks and failures, then In flight counts (running, scheduled in the next 24h, backlog) that open Tasks. Finished rows offer one-click Complete (inline confirm when it would auto-start dependents; the row stays about 6s with Undo) and Review (the full drawer); the group header offers Complete all. Tree members carry a tree chip. External harness alerts remain in the notifications inbox.

## Tasks

Browse all work: Open, Closed or All, every task by state, or only tasks not in a tree. Tree tasks link their tree. A count strip filters to one group; Completed holds the last 7 days. Trees have their own view.

The Dashboard stays available for planning offline. Connect either harness in Settings.

## Answering questions

Needs-input tasks and notifications open the source harness for questions and approvals. T3 uses native links locally and web links on remote desktop targets. OpenCode opens the configured web client. Task detail also offers **Open on service** and **Copy session ID** when a separate client is configured. Settings explains how to register the service on a fresh device.

## References

- Task and tree detail headers have Copy link (a self-describing markdown link, `[stage task #12: Title](…/tasks/12)` or `[stage tree #4: Title](…/trees/4)`, for prompts) and URL (the bare link). Task and tree rows on laptop-width screens show a link icon on hover or keyboard focus, and Alt C in the Ctrl K palette copies the highlighted task or tree.
- Paste a link into a prompt in stage or T3 and ask the agent to read it: `read_ref` / `stage show LINK` returns the task and/or session, or the tree for a tree link, so an agent can add or edit its tasks ([References](/docs/agents#references)).
- Pasted stage task and session links (any host) render as live chips (number or "session", title, state) in prompts, last word and handoff text; tree and unknown links stay plain links.

## Notifications

Needs input, failed, ready and done (historical settled events remain), each toggleable in Settings (one filter for every device), covering tasks and top-level sessions started in either harness (subagents excluded). Every notification also lands in an in-app inbox and toast; a needs-input toast clears once the question is resolved.

- **Browser**: installable PWA with Web Push. The app icon badge counts what needs input. Needs HTTPS or localhost: [Install as an app](/docs/deploy#install-as-an-app-pwa-and-notifications).
- **Desktop app**: native OS notifications from every saved server, also while the window is closed ([Desktop app](/docs/desktop)).

## Search and palette

Ctrl K finds Stage tasks and projects by title. Enter opens the task; Ctrl Enter opens its harness session; Alt C copies its task reference.

## Snippets

Reusable prompt text, global or per project. Type `/` in a task prompt or notes to pick one and insert it.

## Model defaults

T3 tasks prefill provider, model, effort, runtime and mode from a pinned default (Settings), else from your last created task.

## Agents

Agents create, start and manage tasks and trees, and read and write journals, via the `stage` CLI or MCP (stdio or HTTP). See [Agents](/docs/agents).

## Machines

Run harnesses on more than one machine with one main server ([Main server and workers](/docs/deploy#main-server-and-workers)).

- **Settings > Machines** lists every machine, this server first, with online or offline, last seen, its build (flagged when it differs from the server's) and its harness connections. Rename inline; remove a remote machine behind a confirm that says what happens to its worker, connections and tasks.
- **Add machine** creates a one-time pairing link (10 minutes) and the copyable `stage worker join <link>` command, counts down, and shows when the worker joins. Closing it while waiting revokes the code.
- **Per-machine harnesses**: a remote machine's page (Settings > Machines > its name) has the same T3, OpenCode and connection panels, run on that machine through its worker. Credentials stay on the machine. Offline, the page says why and lists its connections read-only.
- **Pickers**: with more than one machine, connection pickers (task and schedule Harness, shared paths, adopt session, project workspaces) tag each harness with its machine. The task and schedule Harness picker lists a chosen project's bound connections first.
- **Projects across machines**: the same Git origin remote and subproject on another machine joins the one project that has it; ambiguous matches wait for a manual bind.

## Settings

The current user (Stage has no sign-in: everything is attributed to one default user), independent T3 and OpenCode connection diagnostics, T3 pairing (Pair with T3 or a pairing code), OpenCode connection (one click for the service on this machine, an `opencode pair` link for another, Disconnect), the T3 URL (locked when `T3_URL` sets it), sync now (a full sync also runs every 5 min), the default model, the notification event filter, and theme. The desktop app adds its saved servers, login startup and joining this machine as a worker of the active remote server ([Desktop app](/docs/desktop#this-machine-as-a-worker)).

Pre-existing external sessions waiting for input appear as silent current-state rows in the inbox when they have no recorded notification group. They add no unread event, push, toast or synthetic history. A recorded group replaces the silent row.

User completion is separate from execution. A task's State picker shows its status and the one manual change it allows; picking Completed (or the Review button on a row) opens a review of cached evidence and dependent impact, with an optional acceptance note. Active work must stop first. Moving a completed task back (the State picker's "Change state") preserves accepted-result history and already claimed attempts, while blocking unclaimed dependents. Later harness activity never revokes acceptance. New trees default to auto and tasks inherit; existing explicit policies remain. Agents report outcomes but have no completion or reopening tool. A connection can also complete a task for you: a successful run whose T3 thread is settled, or whose OpenCode session is archived, is accepted automatically (provenance shown, once per run, changing the state back undoes it; failed or interrupted runs never). Toggle it per connection in Settings (on by default).

Unconfirmed launches reconcile automatically without creating a new attempt. For older launches without safe identity, use **Link existing session** on task detail: paste a session link, preview, then attach. Attachment launches no work.
