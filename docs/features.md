# Features

Detailed behavior of each stage feature. User guide: [stage.hoplabs.dev/docs/concepts](https://stage.hoplabs.dev/docs/concepts). REST contract: [api.md](api.md).

- **Shared access**. Personal opens directly to work, including a desktop on a private socket or a trusted LAN with workers. An owner can opt in per server. In shared mode, members sign in with email and password and share all projects, tasks, machines and harness settings. Admins use **People** for roles, access and member recovery and **Invitations** to copy single-use links. Work activity identifies people, agents, machines and automation. Shared members each have their own inbox read state and device delivery. [Setup and owner recovery](runtime.md#shared-setup-and-owner-recovery)

- **Projects**. Stage owns stable IDs, titles and archive state. The Workspaces panel shows exact catalog rows and connection status. Discovery uses strong evidence to group new rows. Move a workspace to another project or separate it into a new one from that panel. Add workspace (Projects, the Workspaces panel, or the task and schedule form's plus button beside Workspace) asks a connection's harness to add one through a source it declares (its own labels, fields and confirmation); connections that cannot add are listed with the harness's reason. The harness creates and owns it; Stage lists and groups the row it reports, joins it to the project it was added from, and the task form selects it. An unconfirmed outcome offers Check again, which retries the same request safely ([ADR 0012](adr/0012-harness-workspace-add.md)). Project history retains old links, snippets and recorded work. Choose a connection and exact workspace for each task launch or schedule. [Workspace grouping and selection](discovery.md)
- **Tasks**: prompt, connection, exact workspace, then one **Harness · {name}** group drawn only from what the connection declares, in its order and words: model, the harness's options (effort, and launch options such as a new worktree with its base ref and branch where the harness declares them), permission, mode. Optional initial journal note. Save to backlog or start right away. The Session tab prints the chosen launch options (model and each non-default option, in the harness's labels) and the branch and directory the harness reports, marked "reported by {harness}".
- **Journals**: task and tree notes are append-only, with immutable IDs and provenance, optional categories (finding, decision, blocker, outcome), text search, notes/events/all filters, cursor pages (20 by default, 100 maximum), 600-rune previews and full-entry reads. Tree reads aggregate notes from current members; moving a task moves its notes, while tree notes/events stay in their original tree. Move events name both trees in both journals. Membership changes invalidate pagination. Append on closed work never reopens or schedules it. Recorded work protects tasks and trees from deletion, even after a member leaves. Creation/adoption accepts an initial note, schedules retain a note template, duplicates copy no notes. Old task notes are discarded; task event history stays; accurate tree event history starts at rollout.
- **Screenshots**: drop images on the prompt (or Add image; PNG, JPEG, GIF, WebP, up to 8 × 10 MB). They are sent with the prompt on every launch: uploaded to the T3 thread, sent to Codex, or written under Stage's data dir (`claude/images`, never the repository) for Claude Code to open. OpenCode can't take them yet.
- **Live status**: backlog, Launch unconfirmed, running, needs input, done, failed, interrupted or cancelled. Connection loss preserves execution state. User completion in Stage is separate.
- **Task actions**: start, stop, and duplicate when available. Open in the task’s harness or copy its resume command when supplied.
- **Task detail**: Task holds the prompt, handoffs, acceptance, State, Tree, journal, timeline, Config and task actions. Session holds harness actions, launch recovery, requests, messaging and session metadata. The Session attempt switcher opens earlier attempts as read-only snapshots with their last reply, usage and facts. Recent activity shows plan steps, changed files and a bounded feed where available. Full transcripts open in the harness.
- **Answer questions**: Needs-input rows and notifications open Session. Requests shows the questions and approvals its connection declares through `respond`. A single approval can be answered inline on the task or inbox row. Other requests link to `/tasks/:id/session#requests`. For prompts the harness keeps in its own client, use Open in the harness or Copy resume command. Answers are guarded by the task’s state revision, so the first answer wins.
- **Message a session**: The current Session offers Steer and Queue while the turn runs, and Send once the turn ends, where declared by the connection. Ctrl/Cmd+Enter uses the primary delivery. The draft survives tab and attempt changes. A refused message shows the harness’s reason and keeps the draft. A successful delivery shows its mode and time. Messages are text only, up to 32 KiB. Agents use `send_message` or `stage task send` on other tasks’ sessions.
- **Trees**: group tasks into a tree (a DAG; can span projects) where a task needs other members. A task becomes eligible when every need is completed in Stage. Start mode per tree (auto launches, manual marks the task ready and notifies), overridable per task. Blocked tasks cannot start early. Removing a task splices it out: its dependents take over its needs. Mark a tree done when you will not work on the rest (members keep their states, nothing more starts), or archive it; Reopen or Unarchive undoes it, and member activity leaves it closed until explicitly reopened. Done and archived trees and their tasks leave the Dashboard. A standalone task can be archived the same way. Delete is only for work that never started and has no recorded work (deleting a tree deletes its tasks). Dissolve detaches tasks and archives the tree; emptying also archives it. Identity and journals survive. Manual tasks whose needs are completed in Stage (and backlog roots) read ready: they list in the Dashboard Ready group and a `ready` notification (toast and inbox) offers Start. Track session adopts an existing session as a Stage task, which can join a tree. Stage reads the opening prompt when the harness offers it. Views: Trees (sidebar and phone tab; Open | Closed | All, a stat strip by each tree's next step, Active trees most pressing first and Completed in the last 7 days, each tree with its last activity and created date and expandable to its members), Tasks tree members link their tree (opened with the task selected), the tree view (a compact list in level order with each task's needs and time in its state, or a List | Graph toggle to a top-down graph showing execution steps and which needs are met, a side panel, for a selected task, with controls to edit needs, start mode and handoff; Tasks | Notes | Activity tabs, Activity being the tree's full-width event journal), and a Tree panel on task detail with the same controls (or Add to tree: a new tree, or an active one). Handoff (on by default, per task): when a task with needs starts, stage appends one block per accepted need (cached reply excerpt, branch/worktree, task and journal references, and the session ID and link when available) to the prompt, so work carries context forward. Task detail shows what was appended; snapshots stay readable with the source harness offline, and missing replies remain explicitly missing. A dependent's worktree starts where its own launch options say, not from a need's branch; the handoff names the branch each need reported. Tasks saved with a predecessor base were moved to launch options with a journal note: on T3 the worktree starts from its stored base ref (one without a base ref must get one before it starts), on Claude Code and OpenCode from the harness default. A tree can also have a steerer (see Steering).
- **Steering** ([ADR 0013](adr/0013-tree-steering.md), guide `/docs/guides/steering`):
  - **The steerer**: one standalone task bound to a tree (never a member) that hears about member changes and acts on them with ordinary agent operations: answers (first answer wins), accepts, adds follow-ups with `create_task` `treeId` and `needs`, records decisions as tree notes with itself as `sourceTaskId`. Set, replace and stop it in the app, over HTTP, MCP (`set_tree_steerer`, `end_tree_steering`) and CLI (`tree steer`, `tree unsteer`). Its connection must offer send; one without is listed but disabled with the harness's reason. Replace and Stop steering stop the old session where the harness offers stop. Archiving or deleting the steerer task ends steering.
  - **Events and delivery**: while steered, each member transition, answer, readiness, membership change, acceptance, blocker or decision note and tree status change enqueues a durable steering event with who caused it, read as a cursor feed (`get_steering_events`, CLI `tree steering-events`). Stage delivers them to the steerer's session as coalesced `<stage-steering tree=N through=N>` digests: 10 s after the newest event, at most 60 s after the oldest, 32 KiB with a pointer to the feed for the rest, skipping the steerer's own actions. A digest waits for the steerer's current turn to end (Busy retries; other errors back off up to 5 minutes). It is also delivered while the steerer waits on the user, reminding it its question is open, and never to a failed, interrupted or cancelled steerer, whose delivery error reads "steerer not running".
  - **Launch brief and playbook**: the steerer's launch prompt carries a Stage-composed steering brief (the tree's members and their states, its newest notes, the steering rules and the playbook, at most 24 KiB, frozen per attempt), shown in task detail's Prompt panel. The playbook is the global snippet `steering-playbook`, created from Stage's default on first use and edited on the Snippets page; deleting it restores the default on the next launch.
  - **Hold and escalation**: while a live steerer (running, done or needing input) can answer, a member's needs-input notification (push, toast and inbox row) is held for the tree's hold (5 minutes by default, 0 off, at most 1 hour; tree More menu > Steerer hold with off, 2, 5, 10 or 15 minutes, `update_tree steeringHoldSeconds`, CLI `tree edit --hold`). Answered first, nothing notifies; unanswered at expiry, it notifies with "Steerer did not answer"; the steerer escalates at once with `escalate_to_user` (CLI `task escalate`; "Steerer: <reason>"), or asks the user by ending its turn with a question. Losing the steerer releases its holds. A member whose harness offers neither respond nor send is never held. Holds survive restarts.
  - **Tree finish**: when every member is completed, or the tree is marked done or archived, a final digest asks the steerer for an outcome note and ends steering; its next done completes it automatically ("Completed automatically: tree #N finished"), never after a failed or interrupted run, and a person can reopen it.
  - **In the app**: the tree view's steering strip ("No steerer" with Add steerer; the steerer's state, "Last update 2m ago · 3 pending · hold 5 min" and the last delivery error, with Replace and Stop steering; a stopped steerer reads "Steerer stopped. Needs input goes to you."), the steerer drawer (Intent, connection, workspace and launch options; Start steerer or Replace steerer), a Steering panel on the steerer's task detail with its delivery progress and the Steering events feed, a `Steerer · 4m` chip on held task rows (task detail keeps the answer controls), a steered chip on tree rows, steering events in words in tree Activity, and notes on late notifications.
  - **Harnesses** (verified live, see [execution.md](execution.md#steering-live-check)): Claude Code, T3, OpenCode and Codex all host a steerer and let it answer what Stage can answer for them (Requests above); what only the harness can answer (T3 permission requests, Codex permission requests, MCP prompts and secret questions, OpenCode forms with conditional or external fields, Claude prompts open across a Stage restart) stays held until the hold ends unless the steerer escalates it.
- **Sessions**: Track session on Stage or a project, or Add session in a tree, accepts a pasted link or session ID for the selected harness. Preview title, project and state; confirm with an optional task title and initial journal note. Existing owners are reused. No global session browser. The field hint comes from the harness (`sessionHint`; Claude Code: a session UUID, the 8-character ID `claude agents` shows, or a pasted `claude attach` or `--resume` command). Stage refuses a session another harness wraps (T3 declares the Claude Code sessions and Codex threads it starts): a Claude session T3 started reads "This Claude Code session was started by T3. Track it through T3."
- **Transcript**: Conversations, detailed runs and session history stay in the harness. Stage retains the adopted task opening prompt and its bounded final reply.
- **Last word**: The Session tab shows the selected attempt’s latest assistant reply as sanitized markdown (4000 characters, longer replies link to the harness). Task rows show a one-line preview. Cached replies remain available when the harness is offline. Reply polling only runs for task-owned sessions at rest when their updated time changed.
- **Usage**: The Session tab shows a Usage panel in the side column when the task's harness reports what its session consumed (Claude Code does): turns, input tokens (with cache read and cache write below), output tokens, working time once a turn has finished, and cost only when the harness reports one (Claude Code records none). Counts are compact with the exact number on hover; the panel reads "so far" while the task runs or needs input, and is hidden when the harness reports nothing. `stage task show` and `get_task` carry the same usage.
- **Dashboard**: needs-input alert, one alert per connection problem the status button shows ("T3 pairing expired. Fix in Settings"), plus groups in this order across projects: needs input, finished (awaiting user completion), failed, running and ready, then In flight counts (scheduled in 24h, backlog). Tasks outside trees list on their own rows. A tree member never does: its open tree lists once, as its Trees view row (state bar, next step, Start ready, members on expand), under its most pressing step; waiting, completed and closed trees stay off, and In flight counts only tasks outside trees. Finished rows offer one-click Complete (inline confirm when it would auto-start dependents; the row stays about 6s with Undo) and Review (the full drawer); the group header offers Complete all for the tasks outside trees. The sidebar's Dashboard count is the Dashboard's rows (a tree counts once). External harness sessions appear in the notifications inbox.
- **History**: Global session/history browsing is retired. Task and tree journals retain their recorded history.
- **Scheduled tasks**: in the New task drawer pick Start → At time (one-shot: a backlog task starts at that wall time in a chosen zone; a time missed while the server was down starts late) or Repeat (a schedule: presets Hourly / Daily / Weekdays / Weekly or a raw 5-field cron, in its own IANA zone). Choose a connection and exact workspace before saving either timing option. Each recurring fire uses the template's pin and copies its config and images. Fires are skipped while the previous run is pending, running or needs input, when the pin needs repair, or when the server missed the fire. Schedules page, project panel, and a Scheduled (next 24h) group on Stage. Run now, pause/resume, edit, delete (spawned tasks are kept).
- **Back and forward**: on a laptop the sidebar header holds back and forward arrows in the desktop app and the installed web app (a browser tab uses the browser's own); right-click or long-press an arrow lists recent pages. On a phone, Back replaces the logo in the top bar on pages off the tabs (long-press lists pages). Both move through the app's own history only. Every page sets the tab title to its name (`Fix login redirect · stage`, `Tasks · stage-app · stage` under a project scope, `Connections · Settings · stage`), so browser history lists pages by name. The desktop app adds Go > Back/Forward (`Cmd+[`/`Cmd+]`, `Alt+Left`/`Alt+Right`) and the mouse side buttons.
- **Status button**: the first button in the sidebar's bottom row sums up connections in one icon (a check when all is well, an alert in the worst tone with a count from two problems up); its name says which ("All connected", the one problem, or how many need attention). It covers every set-up connection on every machine; a worker that is offline or needs an update counts as a problem. Click it for each connection's state and details, one section per machine when there are several. On a phone the same list is on More, whose tab shows a square while something needs attention.
- **Ctrl K palette**: Jump to Stage tasks, trees, schedules and projects by title, or to a task, tree or schedule by its ID (`409` or `#409`; the exact ID match comes first). Task, tree and schedule rows show their `#id`. Enter opens the result, Ctrl Enter opens the task’s session when a link is available, and Alt C copies its reference.
- **References**: Task, tree, schedule and project headers copy markdown references (`[stage tree #4: Title](…/trees/4)`, `[stage schedule #7: Title](…/schedules/7)`) or bare URLs; each journal row copies `[stage note #45 on task #12](…/tasks/12?entry=45)`. Task and tree rows (hover link icon) and the palette (Alt C, tasks, trees, schedules, projects) copy their links. Pasted task, tree, schedule, project, note and session links render as chips; `/connections/<c>/sessions/<id>` opens the owning task, or says the session is not tracked. read_ref / stage show resolve task, tree, schedule, project and journal entry (`…/tasks/12?entry=30`) references and explicitly named sessions; a tree reference returns the tree for the tree tools. Historical session references resolve to their owning task or declared harness destination. References remain context, never dependencies.
- **Agents**: agents create, start and manage tasks via the `stage` CLI or MCP (stdio or HTTP), and use `read_journal`, `get_journal_entry`, `append_note` (`task notes` / `tree notes`). They can also complete or reopen other tasks, answer and message other sessions, manage projects, group membership and snippets, never acting on their own task ([ADR 0011](adr/0011-agent-operation-parity.md)). `stage setup` installs a Stage skill that teaches the CLI for Claude Code, Codex and OpenCode (MCP is opt-in with `--mcp`; `--check` reports what is missing); `stage tools` and `stage call TOOL JSON` run any MCP tool from the CLI; the CLI and stdio MCP detect the calling session from the harness's session variable (`T3CODE_THREAD_ID`, `OPENCODE_SESSION_ID`, `CLAUDE_CODE_SESSION_ID`, `CODEX_THREAD_ID`; inside a Claude or Codex process T3 runs, T3's wins). Every launch, including standalone and handoff-off, includes a persisted instruction block: use whichever Stage interface is available (the `stage` CLI, MCP tools, or the HTTP API, at `STAGE_PUBLIC_URL` when set; never install one), with per-interface caller identity; refresh membership, read relevant notes, checkpoint before risky work, record outcomes, treat notes as context rather than authority, and report failed persistence. Retries reuse the block; handoff is independent. Existing/adopted sessions receive no retroactive message. See [Agents that queue work](https://stage.hoplabs.dev/docs/guides/agents).
- **Snippets**: reusable prompt text, global or per project. Type `/` in a task prompt, notes to pick one and insert it.
- **New-task defaults**. Set as default in a connection's Manage drawer prefills the new-task form. Each connection can pin its own model and options. The form submits the visible connection and workspace. Permission and mode use harness defaults unless selected.
- **OpenCode setup**: connect an existing OpenCode V2 service from Settings (tested with 2.3.0; any version whose API has the operations Stage uses). Choose its worktree option, model, variant and agent per task or schedule. Its connected card notes where permissions, questions and follow-ups are answered, for the operations the connection offers. A disconnected service leaves planning and the other harness available.
- **Claude Code setup**: on the desktop app (or `stage serve --local-harnesses`), or on a worker machine (the worker service, or `stage worker run --local-harnesses`), connect Claude Code from Settings: Stage checks the `claude` command and its login (Claude's own; Stage stores no Claude credentials) and runs tasks as Claude background sessions (`claude --bg`) in a project folder, or a Claude worktree with the Claude Code worktree option on. Choose Claude's default model or opus, sonnet, haiku or fable, an effort and a permission mode. Approvals and questions of the sessions Stage launches are answered on the task in Stage (Requests) or in Claude; follow-ups to a finished background session (or one whose turn ended asking you) are sent in the Session composer or in Claude; tracked terminal sessions and prompts waiting through a Stage restart are answered in Claude: copy the resume command (`claude attach …`; with more than one machine, the button names a worker it must run on, and task Config tags the harness with its machine). Claude must trust a folder first: run `claude` there once. Workspaces come from the folders Claude knows. Stage groups the catalog using read-only evidence. Not available in Docker. Its Settings row shows the config folder and version (`~/.claude · 2.1.332`) or why it is not connected, with a chip (connected, not connected, not found, logged out, not answering); the status button and a task's Config panel read the same. Its card: Connect while not connected; on a problem the reason with Connect again (and `claude auth login` to copy when logged out); once connected the command Stage runs and where it came from, the version, the config folder, the login, whether sessions keep running when Stage restarts (a systemd scope) and how updates arrive (Updates: "instant · last hook 2m ago" while Claude hooks wake Stage for the sessions it launched, else "every few seconds" with why; the status button adds the same line) and where approvals are answered (Approvals: "on the task in Stage, or in Claude Code" while hooks push, else "in Claude Code"), Check connection and Disconnect (inline confirm); the Claude command field (blank: Stage's own lookup; fixing a missing command reconnects without another Connect); the auto-complete toggle ("Complete tasks when removed in Claude Code": removing a finished session with `claude rm` completes its task). `stage harness claude` prints the same with next steps.
- **Codex setup**: hosted ([ADR 0006](adr/0006-codex-app-server-harness.md)): Stage drives the Codex app-server daemon on the machine Codex runs on: the desktop app or `stage serve --local-harnesses`, or a worker with local harnesses (the worker service, or `stage worker run --local-harnesses`); unavailable in Docker. Connect (Settings or `stage harness codex run connect`) starts the daemon when it is down (Stage never stops it) and connects the Codex home; log in with `codex login`, Stage stores no Codex credentials. States: connected, not connected, signed out, unreachable, not installed, each problem with the command that fixes it. Setting: Codex CLI path (empty: `codex` on PATH). Root workspace only (no Codex worktrees), no Plan mode, images supported; permission Read only, Auto (default) or Full access. Workspaces are the projects Codex trusts (trust them in Codex). Command and file-change approvals and Codex's questions are answered in Stage (Requests), and Send in the Session composer starts a new turn once the thread is idle; permission requests, MCP prompts and secret questions are answered in Codex: task rows, notifications and task detail offer Copy resume command (`cd <dir> && codex resume <id>`). Track session takes a thread id or a `codex resume <id>` command; T3 Code's threads are refused ("Track it through T3"). Archive in Codex completes the task (toggle "Complete tasks when archived in Codex").
- **T3 setup**: optional, like OpenCode; T3 is not a default harness. A first run has no connections (pairing creates the T3 connection); the Dashboard shows a "Connect a harness" alert whenever nothing is connected, linking to Settings > Connections. T3 counts as connected only once paired (a stored token or a saved admin token); an unpaired T3 has no row and is never contacted in the background. Discovery lists reported T3 workspaces and organizes them into project groups.
- **Machines**: Settings > Connections lists every machine (the main machine, where Stage runs, first; the rest are workers) as a compact group: online/offline, last seen, build (flagged when it differs from the main machine's) and its harness connections as rows. Rename a worker inline; remove a worker behind an inline confirm that says what happens to its worker, connections and tasks. Add connection (per machine) lists the harnesses that machine can still connect, the connected ones disabled; Manage opens the connection's setup in a drawer, driven on that machine through its worker, with copy naming the machine, and once it is set up a Capabilities list: one line per operation the harness declares (Start tasks, Stop from Stage, Send follow-ups, ...), available or unavailable with the harness's reason; credentials stay on the machine; Disconnect asks inline and the row stays as Disconnected: the instance and its recorded work, an idle "disconnected" chip, Reconnect (opens its setup) and Remove connection (inline confirmation, also available in the Reconnect drawer on phones). Removing a connection preserves its task history. Retired connections appear under Previous connections. Their last-known workspace rows are available through project history and are excluded from launch pickers. A connection never set up (no instance, nothing on it) is not a row. A disconnected T3 whose environment is connected on another machine (paired again from a worker) retires onto that connection automatically, at the next sync. The header counts connected rows only. With no connections the group reads "No connections. Connect a harness to run tasks here." with Connect T3 and Connect OpenCode. Offline or on another version, a machine's group says why and lists its connections on record, read-only. Add machine creates a one-time 10 minute pairing link and the copyable `stage worker join <link>` command, counts down, and flips from waiting to joined when the worker redeems it; closing it while waiting revokes the code. Old `/settings/machines/:id` links land on Connections. With more than one machine, connection pickers (task and schedule Harness, adopt session, project workspaces) tag each harness with its machine; with one machine they read as before. The task and schedule forms list workspaces on the selected connection. A saved workspace on a disconnected connection is shown with its availability so it can be repaired.
- **Settings**: General shows the personal user, theme and Info (the running server's version, how it runs, start time, identity, socket or URL, the desktop app's state and Open Stage at login, copy diagnostics). On desktop, General also shows **Servers** for adding and switching installations. Connections shows machines and their harness connections, with **Sync now** and per-connection launch defaults. T3 Disconnect forgets its token, T3 URL, Browser URL and admin token and stops syncing. Tasks and workspace history stay and pairing the same T3 resumes the connection. Manage holds T3 pairing, those URLs, the optional admin token and New tasks (Set as default, model pin). OpenCode Disconnect forgets its address and credentials. Harness settings live in Stage. Notifications manages delivery and per-event toggles. On a shared server, **Account** manages name, password, agent credential and sign-out.
- **Notifications**: installable PWA with Web Push for needs input, failed, ready and done, each toggleable in Settings. Notifications cover tasks and supported external sessions (subagents excluded). A steered tree member's needs input waits for its steerer first (see Trees: steering). The app icon badge counts unread events for a shared account and needs-input work on a personal server. Needs HTTPS or localhost. [HTTPS and push notifications](../README.md#https-and-push-notifications)

Pre-existing external T3 sessions waiting for input appear as silent current-state rows in the inbox when they have no recorded notification group. They add no unread event, push, toast or synthetic history. A recorded group replaces the silent row. Local Claude Code sessions waiting for input (background ones, also after Claude retired them, and terminal or IDE ones; not T3's) always appear this way and never notify. A row shows its project or folder and its way back: Open in the harness, Copy resume command (`claude attach <id>`, shown under the row), or "Answer in Claude Code" for a terminal session. Track opens Track session with the session filled in; it becomes a task only when you confirm.

User completion is separate from execution. A task's State picker (tree side panel, task detail State panel) shows its status and the one manual change it allows; picking Completed (or the Review button on a row) opens a review of cached evidence and dependent impact, with an optional acceptance note. Active work must stop first. Moving a completed task back (State picker: back to "to review", "ready"... in a "Change state" drawer) preserves accepted-result history and already claimed attempts, while blocking unclaimed dependents. Later execution activity never revokes acceptance. New trees default to auto and tasks inherit; existing explicit policies remain. Agents can complete and reopen other tasks through the same review (`get_completion_preview`, then `complete_task`), never their own; they report their own outcome in notes. A connection can also complete a task for you: a successful run whose T3 thread is settled, whose OpenCode session or Codex thread is archived, or whose Claude Code session is removed (`claude rm`) after its turn ended, is accepted automatically (provenance shown, once per run, changing the state back undoes it; failed or interrupted runs never). Toggle it per connection in Settings (on by default).

Unconfirmed launches reconcile automatically without creating a new attempt. The Session tab shows why the last check failed, how many failed and the next retry; when the harness started a session Stage could not record yet, it says so and offers the session link or resume command when supplied. For launches without a confirmed identity, use **Link existing session** on the Session tab. Enter the session reference, preview it and confirm. Attachment launches no work.
