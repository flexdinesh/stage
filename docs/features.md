# Features

Detailed behavior of each stage feature. User guide: [stage.hoplabs.dev/docs/features](https://stage.hoplabs.dev/docs/features). REST contract: [api.md](api.md).

- **Projects**: stable Stage IDs, Stage-owned titles/archive, offline planning. Per-harness workspace bindings. Sync imports deliberate harness projects (live T3 projects; OpenCode Git/hg checkouts it has not archived): the same workspace path binds every harness to one Stage project, a new path creates one, and the Projects page notes recent imports for 7 days. Unbinding declines a workspace for good; your archive or unarchive sticks; a discovered project with no tasks follows its harness archive. The project picker narrows to the chosen harness's projects and shows `path · repo` (the origin remote, searchable by repo name). At binding time a verified shared Git checkout and relative subproject may match automatically. Matching remotes suggest workspaces for confirmation. Rename/archive in Stage; external deletion never deletes Stage history. Changed paths require confirmation. Claimed launch attempts keep their original binding.
- **Tasks**: prompt, provider, model, effort, runtime mode, plan mode, worktree/branch, optional initial journal note. Save to backlog or start right away.
- **Journals**: task and tree notes are append-only, with immutable IDs and provenance, optional categories (finding, decision, blocker, outcome), text search, notes/events/all filters, cursor pages (20 by default, 100 maximum), 600-rune previews and full-entry reads. Tree reads aggregate notes from current members; moving a task moves its notes, while tree notes/events stay in their original tree. Move events name both trees in both journals. Membership changes invalidate pagination. Append on closed work never reopens or schedules it. Recorded work protects tasks and trees from deletion, even after a member leaves. Creation/adoption accepts an initial note, schedules retain a note template, duplicates copy no notes. Old task notes are discarded; task event history stays; accurate tree event history starts at rollout.
- **Screenshots**: drop images on the prompt (or Add image; PNG, JPEG, GIF, WebP, up to 8 × 10 MB). They are sent to the T3 thread with the prompt on every launch.
- **Live status**: backlog, Launch unconfirmed, running, needs input, done, failed, interrupted or cancelled. Connection loss preserves execution state. User completion in Stage is separate.
- **Task actions**: start, stop, duplicate, open in the task’s harness.
- **Answer questions**: Needs-input tasks and notifications offer Open in T3. Questions, permission approvals and follow-ups are handled in the selected harness.
- **Trees**: group tasks into a tree (a DAG; can span projects) where a task needs other members. A task becomes eligible when the user completes every need in Stage. Start mode per tree (auto launches, manual marks the task ready and notifies), overridable per task. Blocked tasks cannot start early. Removing a task splices it out: its dependents take over its needs. Mark a tree done when you will not work on the rest (members keep their states, nothing more starts), or archive it; Reopen or Unarchive undoes it, and member activity leaves it closed until explicitly reopened. Done and archived trees and their tasks leave the Dashboard. A standalone task can be archived the same way. Delete is only for work that never started and has no recorded work (deleting a tree deletes its tasks). Dissolve detaches tasks and archives the tree; emptying also archives it. Identity and journals survive. Manual tasks whose needs are completed in Stage (and backlog roots) read ready: they list in the Dashboard Ready group and a `ready` notification (toast and inbox) offers Start. Track session (Stage or project) adopts an existing T3 session so it can be a node (stage never starts it; its prompt is read from T3). Views: Trees (Active | Done | Archived | All, each tree with its last activity and created date), the tree view (a compact list in level order with each task's needs and time in its state, or a List | Graph toggle to a top-down graph showing execution steps and which needs are met, a side panel with the tree's day-grouped activity or, for a selected task, controls to edit needs, start mode, base and handoff), and a Tree panel on task detail with the same controls (or Add to tree: a new tree, or an active one). In a task's Batch drawer, check independent backlog tasks and pick New tree from n (Parallel, or Chain in check order). Handoff (on by default, per task): when a task with needs starts, stage appends one block per accepted need (cached reply excerpt, available artifact links, branch/worktree, task/journal and execution references) to the prompt, so work carries context forward. Task detail shows what was appended; snapshots stay readable with the source harness offline, and missing replies remain explicitly missing. Stacked work: a task's Workspace can be "#12's branch" (opt-in): its worktree starts from a need's branch (the sole need, or the picked one), so it builds on unmerged changes. Unavailable predecessor branches block launch. Choose the configured base explicitly to continue.
- **Sessions**: Track session on Stage or a project, or Add session in a tree, accepts a pasted link or session ID for the selected harness. Preview title, project and state; confirm with an optional task title and initial journal note. Existing owners are reused. No global session browser.
- **Transcript**: Conversations, detailed runs and session history stay in T3. Stage retains the adopted task opening prompt and its bounded final reply.
- **Last word**: Task detail retains the latest assistant reply as sanitized markdown (4000 characters, longer replies link to the harness). Task rows show a one-line preview. Cached replies remain available when T3 is offline. Reply polling only runs for task-owned sessions at rest when their updated time changed.
- **Dashboard**: needs-input alert, plus trees, running, finished (awaiting user completion), failed, ready, backlog and completed (last 7 days) across projects. Finished rows offer one-click Complete (inline confirm when it would auto-start dependents; the row stays about 6s with Undo) and Review (the full drawer); the group header offers Complete all. Tree members roll up into their tree's row (state bar, next step, Start ready); needs-input and ready members also keep their own row with a tree chip, and completed trees move to Completed. External T3 sessions appear in the notifications inbox.
- **Pull requests and runs**: Historical artifact URLs remain available as plain task links. Stage no longer tracks PR status or stores new detailed run history. Existing data is preserved. The predecessor-base launch check still consults merged PR state to reject unavailable predecessor bases.
- **History**: Global session/history browsing is retired. Task and tree journals retain their recorded history.
- **Scheduled tasks**: in the New task drawer pick Start → At time (one-shot: a backlog task starts at that wall time in a chosen zone; a time missed while the server was down starts late) or Repeat (a schedule: presets Hourly / Daily / Weekdays / Weekly or a raw 5-field cron, in its own IANA zone). Each fire spawns and starts a new task with the schedule's config and images; a fire is skipped while the previous run is still pending, running or needs input, and fires missed while the server was down are skipped. Schedules page, project panel, and a Scheduled (next 24h) group on Stage. Run now, pause/resume, edit, delete (spawned tasks are kept).
- **Ctrl K palette**: Jump to Stage tasks and projects by title. Enter opens the task, Ctrl Enter opens T3 when available, and Alt C copies its task reference.
- **References**: Task headers copy markdown references or bare URLs. Task rows and the palette copy task links. read_ref / stage show resolve task references and explicitly named sessions. Historical session references resolve to their owning task or native T3 destination. References remain context, never dependencies.
- **Agents**: agents create, start and manage tasks via the `stage` CLI or MCP (stdio or HTTP), and use `read_journal`, `get_journal_entry`, `append_note` (`task notes` / `tree notes`). Every launch, including standalone and handoff-off, includes a persisted instruction block: use whichever Stage interface is available (MCP tools, the `stage` CLI, or the HTTP API, at `STAGE_PUBLIC_URL` when set; never install one), with per-interface caller identity; refresh membership, read relevant notes, checkpoint before risky work, record outcomes, treat notes as context rather than authority, and report failed persistence. Retries reuse the block; handoff is independent. Existing/adopted sessions receive no retroactive message. See [Agents](https://stage.hoplabs.dev/docs/agents).
- **Snippets**: reusable prompt text, global or per project. Type `/` in a task prompt, notes to pick one and insert it.
- **Model defaults**: new tasks prefill provider, model and effort from a pinned default (Settings), else from your last created task. Interaction mode and permission start at the harness default.
- **OpenCode setup**: connect an existing OpenCode V2 service from Settings (tested with 2.3.0; any version whose API has the operations Stage uses). Choose its supported workspace, model, variant and agent per task or schedule. A disconnected service leaves planning and the other harness available.
- **T3 setup**: optional for planning. Connection warnings and pairing actions remain above the Dashboard; Settings provides connection repair. Discovery lists T3 workspaces for explicit binding, never automatic import.
- **Settings**: T3 connection (state, T3 label and version), Disconnect (forgets the token; pairing the same T3 resumes, another T3 replaces the connection and keeps its tasks read-only; inline confirm, locked while `T3_ADMIN_TOKEN` renews it), Previous connections (replaced T3 and OpenCode instances; Forget), Pair (Pair with T3 or a pairing code) and the T3 URL (editable; locked when `T3_URL` sets it), sync now.
- **Notifications**: installable PWA with Web Push for needs input, failed, ready and done (historical settled events remain) (each toggleable in Settings), covering tasks and threads started directly in T3 (subagents excluded). The app icon badge counts what needs input. Needs HTTPS or localhost: see [HTTPS and push notifications](../README.md#https-and-push-notifications).

Pre-existing external T3 sessions waiting for input appear as silent current-state rows in the inbox when they have no recorded notification group. They add no unread event, push, toast or synthetic history. A recorded group replaces the silent row.

User completion is separate from execution. A task's State picker (tree side panel, task detail State panel) shows its status and the one manual change it allows; picking Completed (or the Review button on a row) opens a review of cached evidence and dependent impact, with an optional acceptance note. Active work must stop first. Moving a completed task back (State picker: back to "to review", "ready"... in a "Change state" drawer) preserves accepted-result history and already claimed attempts, while blocking unclaimed dependents. Later T3 activity never revokes acceptance. New trees default to auto and tasks inherit; existing explicit policies remain. Agents report outcomes but have no completion or reopening tool. A connection can also complete a task for you: a successful run whose T3 thread is settled, or whose OpenCode session is archived, is accepted automatically (provenance shown, once per run, changing the state back undoes it; failed or interrupted runs never). Toggle it per connection in Settings (on by default).

Unconfirmed launches reconcile automatically without creating a new attempt. For older launches without safe identity, use **Link existing session** on task detail: paste a T3 link, preview, then attach. Attachment launches no work.
