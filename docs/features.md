# Features

Detailed behavior of each stage feature. User guide: [stage.hoplabs.dev/docs/concepts](https://stage.hoplabs.dev/docs/concepts). REST contract: [api.md](api.md).

- **Projects**: stable Stage IDs, Stage-owned titles/archive, offline planning. Per-harness workspace bindings. Sync imports deliberate harness projects (live T3 projects; OpenCode Git/hg checkouts it has not archived; Git checkouts Codex trusts): the same workspace path binds every harness on a machine to one Stage project, the same Git origin remote and subproject on another machine joins the one project that has it (ambiguous matches wait for a manual bind; no remote, no cross-machine merge), a new workspace creates one, and the Projects page notes recent imports for 7 days. Unbinding declines a workspace for good; your archive or unarchive sticks; a discovered project with no tasks follows its harness archive. The project picker narrows to the chosen harness's projects and shows `path · repo` (the origin remote, searchable by repo name). At binding time a verified shared Git checkout and relative subproject may match automatically. Matching remotes (and subprojects) suggest workspaces for confirmation. Rename/archive in Stage; external deletion never deletes Stage history. Changed paths require confirmation. Claimed launch attempts keep their original binding.
- **Tasks**: prompt, provider, model, effort, runtime mode, plan mode, worktree/branch, optional initial journal note. Save to backlog or start right away.
- **Journals**: task and tree notes are append-only, with immutable IDs and provenance, optional categories (finding, decision, blocker, outcome), text search, notes/events/all filters, cursor pages (20 by default, 100 maximum), 600-rune previews and full-entry reads. Tree reads aggregate notes from current members; moving a task moves its notes, while tree notes/events stay in their original tree. Move events name both trees in both journals. Membership changes invalidate pagination. Append on closed work never reopens or schedules it. Recorded work protects tasks and trees from deletion, even after a member leaves. Creation/adoption accepts an initial note, schedules retain a note template, duplicates copy no notes. Old task notes are discarded; task event history stays; accurate tree event history starts at rollout.
- **Screenshots**: drop images on the prompt (or Add image; PNG, JPEG, GIF, WebP, up to 8 × 10 MB). They are sent to the T3 thread with the prompt on every launch.
- **Live status**: backlog, Launch unconfirmed, running, needs input, done, failed, interrupted or cancelled. Connection loss preserves execution state. User completion in Stage is separate.
- **Task actions**: start, stop, duplicate, open in the task’s harness.
- **Answer questions**: Needs-input tasks and notifications offer Open in T3. Questions, permission approvals and follow-ups are handled in the selected harness.
- **Trees**: group tasks into a tree (a DAG; can span projects) where a task needs other members. A task becomes eligible when the user completes every need in Stage. Start mode per tree (auto launches, manual marks the task ready and notifies), overridable per task. Blocked tasks cannot start early. Removing a task splices it out: its dependents take over its needs. Mark a tree done when you will not work on the rest (members keep their states, nothing more starts), or archive it; Reopen or Unarchive undoes it, and member activity leaves it closed until explicitly reopened. Done and archived trees and their tasks leave the Dashboard. A standalone task can be archived the same way. Delete is only for work that never started and has no recorded work (deleting a tree deletes its tasks). Dissolve detaches tasks and archives the tree; emptying also archives it. Identity and journals survive. Manual tasks whose needs are completed in Stage (and backlog roots) read ready: they list in the Dashboard Ready group and a `ready` notification (toast and inbox) offers Start. Track session (Stage or project) adopts an existing T3 session so it can be a node (stage never starts it; its prompt is read from T3). Views: Trees (sidebar and phone tab; Open | Closed | All, a stat strip by each tree's next step, Active trees most pressing first and Completed in the last 7 days, each tree with its last activity and created date and expandable to its members), Tasks tree members link their tree (opened with the task selected), the tree view (a compact list in level order with each task's needs and time in its state, or a List | Graph toggle to a top-down graph showing execution steps and which needs are met, a side panel, for a selected task, with controls to edit needs, start mode, base and handoff; Tasks | Notes | Activity tabs, Activity being the tree's full-width event journal), and a Tree panel on task detail with the same controls (or Add to tree: a new tree, or an active one). In a task's Batch drawer, check independent backlog tasks and pick New tree from n (Parallel, or Chain in check order). Handoff (on by default, per task): when a task with needs starts, stage appends one block per accepted need (cached reply excerpt, available artifact links, branch/worktree, task/journal and execution references) to the prompt, so work carries context forward. Task detail shows what was appended; snapshots stay readable with the source harness offline, and missing replies remain explicitly missing. Stacked work: a task's Workspace can be "#12's branch" (opt-in): its worktree starts from a need's branch (the sole need, or the picked one), so it builds on unmerged changes. Unavailable predecessor branches block launch. Choose the configured base explicitly to continue.
- **Sessions**: Track session on Stage or a project, or Add session in a tree, accepts a pasted link or session ID for the selected harness. Preview title, project and state; confirm with an optional task title and initial journal note. Existing owners are reused. No global session browser.
- **Transcript**: Conversations, detailed runs and session history stay in T3. Stage retains the adopted task opening prompt and its bounded final reply.
- **Last word**: Task detail retains the latest assistant reply as sanitized markdown (4000 characters, longer replies link to the harness). Task rows show a one-line preview. Cached replies remain available when T3 is offline. Reply polling only runs for task-owned sessions at rest when their updated time changed.
- **Dashboard**: needs-input alert, plus trees, running, finished (awaiting user completion), failed, ready, backlog and completed (last 7 days) across projects. Finished rows offer one-click Complete (inline confirm when it would auto-start dependents; the row stays about 6s with Undo) and Review (the full drawer); the group header offers Complete all. Tree members roll up into their tree's row (state bar, next step, Start ready); needs-input and ready members also keep their own row with a tree chip, and completed trees move to Completed. External T3 sessions appear in the notifications inbox.
- **Pull requests and runs**: Historical artifact URLs remain available as plain task links. Stage no longer tracks PR status or stores new detailed run history. Existing data is preserved. The predecessor-base launch check still consults merged PR state to reject unavailable predecessor bases.
- **History**: Global session/history browsing is retired. Task and tree journals retain their recorded history.
- **Scheduled tasks**: in the New task drawer pick Start → At time (one-shot: a backlog task starts at that wall time in a chosen zone; a time missed while the server was down starts late) or Repeat (a schedule: presets Hourly / Daily / Weekdays / Weekly or a raw 5-field cron, in its own IANA zone). Each fire spawns and starts a new task with the schedule's config and images; a fire is skipped while the previous run is still pending, running or needs input, and fires missed while the server was down are skipped. Schedules page, project panel, and a Scheduled (next 24h) group on Stage. Run now, pause/resume, edit, delete (spawned tasks are kept).
- **Back and forward**: on a laptop the sidebar header holds back and forward arrows in the desktop app and the installed web app (a browser tab uses the browser's own); right-click or long-press an arrow lists recent pages. On a phone, Back replaces the logo in the top bar on pages off the tabs (long-press lists pages). Both move through the app's own history only. Every page sets the tab title to its name (`Fix login redirect · stage`, `Tasks · stage-app · stage` under a project scope, `Connections · Settings · stage`), so browser history lists pages by name. The desktop app adds Go > Back/Forward (`Cmd+[`/`Cmd+]`, `Alt+Left`/`Alt+Right`) and the mouse side buttons.
- **Status button**: the first button in the sidebar's bottom row sums up connections in one icon (a check when all is well, an alert in the worst tone with a count from two problems up); its name says which ("All connected", the one problem, or how many need attention). It covers every set-up connection on every machine; a worker that is offline or needs an update counts as a problem. Click it for each connection's state and details, one section per machine when there are several. On a phone the same list is on More, whose tab shows a square while something needs attention.
- **Ctrl K palette**: Jump to Stage tasks, trees and projects by title, or to a task or tree by its ID (`409` or `#409`; the exact ID match comes first). Task and tree rows show their `#id`. Enter opens the task, Ctrl Enter opens T3 when available, and Alt C copies its task reference.
- **References**: Task and tree headers copy markdown references (`[stage tree #4: Title](…/trees/4)`) or bare URLs. Task and tree rows (hover link icon) and the palette (Alt C) copy their links. read_ref / stage show resolve task and tree references and explicitly named sessions; a tree reference returns the tree for the tree tools. Historical session references resolve to their owning task or native T3 destination. References remain context, never dependencies.
- **Agents**: agents create, start and manage tasks via the `stage` CLI or MCP (stdio or HTTP), and use `read_journal`, `get_journal_entry`, `append_note` (`task notes` / `tree notes`). `stage setup` installs a Stage skill that teaches the CLI for Claude Code, Codex and OpenCode (MCP is opt-in with `--mcp`; `--check` reports what is missing); `stage tools` and `stage call TOOL JSON` run any MCP tool from the CLI; the CLI and stdio MCP detect the calling session from the harness's session variable (`T3CODE_THREAD_ID`, `OPENCODE_SESSION_ID`, `CLAUDE_CODE_SESSION_ID`, `CODEX_THREAD_ID`; inside a Claude or Codex process T3 runs, T3's wins). Every launch, including standalone and handoff-off, includes a persisted instruction block: use whichever Stage interface is available (the `stage` CLI, MCP tools, or the HTTP API, at `STAGE_PUBLIC_URL` when set; never install one), with per-interface caller identity; refresh membership, read relevant notes, checkpoint before risky work, record outcomes, treat notes as context rather than authority, and report failed persistence. Retries reuse the block; handoff is independent. Existing/adopted sessions receive no retroactive message. See [Agents that queue work](https://stage.hoplabs.dev/docs/guides/agents).
- **Snippets**: reusable prompt text, global or per project. Type `/` in a task prompt, notes to pick one and insert it.
- **New-task defaults**: per connection, in its Manage drawer's New tasks panel. Set as default makes a connection (one across all machines) the one the new-task form, Ctrl K, quick add and agents start on; the connection row shows a `default` chip. A project not available there opens on its first available harness (the main machine's first), and the form says so. Each connection pins its own model and options (any harness, from its capabilities); unpinned, new tasks there start at the harness default. Interaction mode and permission always start at the harness default. Harness-specific new-task settings belong in the same panel.
- **OpenCode setup**: connect an existing OpenCode V2 service from Settings (tested with 2.3.0; any version whose API has the operations Stage uses). Choose its supported workspace, model, variant and agent per task or schedule. A disconnected service leaves planning and the other harness available.
- **Claude Code setup**: on the desktop app (or `stage serve --local-harnesses`), connect Claude Code from Settings: Stage checks the `claude` command and its login (Claude's own; Stage stores no Claude credentials) and runs tasks as Claude background sessions (`claude --bg`) in a project folder or a Claude worktree. Choose Claude's default model or opus, sonnet, haiku or fable, an effort and a permission mode. Questions and approvals are answered in Claude: copy the resume command (`claude attach …`). Claude must trust a folder first: run `claude` there once. Projects come from the folders Claude knows; Git checkouts import. Not available in Docker or on worker machines yet.
- **Codex setup**: hosted ([ADR 0006](adr/0006-codex-app-server-harness.md)): Stage drives the Codex app-server daemon on the machine it runs on, so only in the desktop app or `stage serve --local-harnesses`; unavailable in Docker and on workers. Connect (Settings or `stage harness codex run connect`) starts the daemon when it is down (Stage never stops it) and connects the Codex home; log in with `codex login`, Stage stores no Codex credentials. States: connected, not connected, signed out, unreachable, not installed, each problem with the command that fixes it. Setting: Codex CLI path (empty: `codex` on PATH). Root workspace only (no Codex worktrees), no Plan mode, images supported; permission Read only, Auto (default) or Full access. Workspaces are the projects Codex trusts (trust them in Codex). Questions and approvals are answered in Codex: task rows and task detail offer Copy resume command (`cd <dir> && codex resume <id>`). Track session takes a thread id or a `codex resume <id>` command; T3 Code's threads are refused ("Track it through T3"). Archive in Codex completes the task (toggle "Complete tasks when archived in Codex").
- **T3 setup**: optional, like OpenCode. A first run has no connections; the Dashboard shows a "Connect a harness" alert whenever nothing is connected, linking to Settings > Connections. T3 counts as connected only once paired (a stored token or a saved admin token); an unpaired T3 has no row and is never contacted in the background. Discovery lists T3 workspaces for explicit binding, never automatic import.
- **Machines**: Settings > Connections lists every machine (the main machine, where Stage runs, first; the rest are workers) as a compact group: online/offline, last seen, build (flagged when it differs from the main machine's) and its harness connections as rows. Rename a worker inline; remove a worker behind an inline confirm that says what happens to its worker, connections and tasks. Add connection (per machine) lists the harnesses that machine can still connect, the connected ones disabled; Manage opens the connection's setup in a drawer, driven on that machine through its worker, with copy naming the machine; credentials stay on the machine; Disconnect asks inline and the row stays as Disconnected: the instance and what stays on it ("controlbox · 400 tasks · 27 bindings"), an idle "disconnected" chip, Reconnect (opens its setup) and Forget (inline confirm; on phone, in the Reconnect drawer). Forget retires it and lets go of it; its tasks keep their history, read-only. A connection never set up (no instance, nothing on it) is not a row. A disconnected T3 whose environment is connected on another machine (paired again from a worker) retires onto that connection automatically, at the next sync. The header counts connected rows only. With no connections the group reads "No connections. Connect a harness to run tasks here." with Connect T3 and Connect OpenCode. Offline or on another version, a machine's group says why and lists its connections on record, read-only. Add machine creates a one-time 10 minute pairing link and the copyable `stage worker join <link>` command, counts down, and flips from waiting to joined when the worker redeems it; closing it while waiting revokes the code. Old `/settings/machines/:id` links land on Connections. With more than one machine, connection pickers (task and schedule Harness, adopt session, project workspaces) tag each harness with its machine; with one machine they read as before. The task and schedule Harness picker lists a chosen project's bound connections first and marks the rest "not bound". Pickers and project workspaces list connected harnesses only; a task or schedule already on a disconnected one shows it disabled as "(disconnected)", and a disconnected default or binding never picks where a task goes.
- **Settings**: three tabs. General: User (the current user, read-only; no sign-in, so everything is attributed to the default user), theme, and Info (the running server's version, how it runs, start time, identity, socket or URL, the desktop app's state and Open Stage at login, copy diagnostics). Connections: machines and their harness connections (above), sync now; T3 Disconnect (inline confirm, never locked) forgets the token, the T3 URL, the Browser URL and the admin token and stops syncing; tasks and bindings stay and pairing the same T3 again resumes it. Pair (Pair with T3 or a pairing code), the T3 URL, the Browser URL (for Open in T3 links; empty = the T3 URL) and the optional admin token (lets Stage renew the T3 token automatically) live in its Manage drawer, with its New tasks panel (Set as default, model pin). OpenCode Disconnect forgets its address and credentials, also never locked. No harness setting comes from the environment. Notifications: delivery and per-event toggles. The app assumes one server, this machine's: server switching is kept in code but not offered in the UI.
- **Notifications**: installable PWA with Web Push for needs input, failed, ready and done (historical settled events remain) (each toggleable in Settings), covering tasks and threads started directly in T3 (subagents excluded). The app icon badge counts what needs input. Needs HTTPS or localhost: see [HTTPS and push notifications](../README.md#https-and-push-notifications).

Pre-existing external T3 sessions waiting for input appear as silent current-state rows in the inbox when they have no recorded notification group. They add no unread event, push, toast or synthetic history. A recorded group replaces the silent row.

User completion is separate from execution. A task's State picker (tree side panel, task detail State panel) shows its status and the one manual change it allows; picking Completed (or the Review button on a row) opens a review of cached evidence and dependent impact, with an optional acceptance note. Active work must stop first. Moving a completed task back (State picker: back to "to review", "ready"... in a "Change state" drawer) preserves accepted-result history and already claimed attempts, while blocking unclaimed dependents. Later T3 activity never revokes acceptance. New trees default to auto and tasks inherit; existing explicit policies remain. Agents report outcomes but have no completion or reopening tool. A connection can also complete a task for you: a successful run whose T3 thread is settled, whose OpenCode session or Codex thread is archived, or whose Claude Code session is removed (`claude rm`) after its turn ended, is accepted automatically (provenance shown, once per run, changing the state back undoes it; failed or interrupted runs never). Toggle it per connection in Settings (on by default).

Unconfirmed launches reconcile automatically without creating a new attempt. Task detail shows why the last check failed, how many failed and the next retry; when the harness started a session Stage could not record yet, it says so and offers **Open in T3** for that session. For older launches without safe identity, use **Link existing session** on task detail: paste a T3 link, preview, then attach. Attachment launches no work.
