# Product

<!-- impeccable:product-schema 1 -->

## Platform

web

## Users
Developers running T3 Code, OpenCode, Codex and Claude Code sessions across several projects. They use stage mostly from a laptop and a phone on their private network, rarely a desktop: queueing work, checking what needs input, and glancing at what is running or done.

## Product Purpose
A self-hosted task manager for T3 Code, OpenCode V2, Codex and Claude Code. Users plan tasks, review final replies, complete work and start ready dependents across projects.

## Positioning
Stage owns projects, tasks, trees, schedules, journals, acceptance and durable handoff: it launches a task into a harness and keeps up with its progress. T3, OpenCode, Codex and Claude Code own sessions and everything in them: conversations, questions, approvals, execution, workspaces, worktrees and branches ([ADR 0007](docs/adr/0007-harness-boundary.md)). Stage-wide features work across harnesses or adapt to declared capabilities, while each harness keeps its own scoped extras, settings, setup panel and vocabulary ([ADR 0008 P2–P3](docs/adr/0008-harness-foundation.md#p2)).

## Operating Context
- Self-hosted on the T3 host via docker compose, listening on 127.0.0.1:7380 by default (compose publishes it on host loopback; expose it only on a trusted private network or behind a proxy), no auth.
- Or as a per-user OS service with the Linux/macOS desktop app: the same UI in a native window over the local Unix socket; the app starts the service, stays resident when its window closes and shows native notifications and a needs-input badge while resident; Quit stops them and leaves the server running. Phones and other machines keep using the browser.
- The desktop app can also switch to saved remote Stage servers on a trusted network (no auth, plain TCP to that server's listener; a hostname needs that server's `STAGE_ALLOWED_ORIGINS`). One server at a time in the window (Settings Servers: add with Test connection, edit, remove, switch; a top-bar server menu once more than one is saved); notifications and the badge cover every saved server. Open in T3 uses native links locally and T3 web links for remote servers. Each Stage server owns its harness connections; the desktop never starts or configures a remote.
- One existing T3 MCP service and one existing OpenCode V2 service may be used independently or together. Each instance (a T3 environment, an OpenCode service) is its own connection; one per harness is active. Replacing an instance keeps the old connection's tasks and bindings as read-only history while discovery resolves workspaces on the new connection. Reconnecting the old instance restores its tasks and bindings.
- Codex is hosted: Stage drives the Codex app-server daemon on the machine it runs on (desktop app, or `stage serve --local-harnesses`) or on a worker with local harnesses (the worker service, or `stage worker run --local-harnesses`), never in Docker. Connect starts the daemon when it is down; Stage never stops it and stores no Codex credentials (`codex login`). Its connection is the Codex home. Questions and approvals are answered in Codex through a copied `codex resume` command.
- Claude Code runs as Claude background sessions (`claude --bg`) on the machine Stage runs on (the desktop app, or `stage serve --local-harnesses`) or on a worker with local harnesses (the worker service, or `stage worker run --local-harnesses`), never in Docker, signed in with Claude's own login; Stage stores no Claude credentials. Its connection is named by Claude's config folder.
- Only acceptance in Stage releases dependent tasks: user completion, or a per-connection auto-complete (on by default) when a successful run's T3 thread is settled, OpenCode session or Codex thread is archived, or Claude Code session is removed (`claude rm`). New trees default to auto start; tasks inherit.

## Capabilities and Constraints
- Projects have stable Stage IDs and Stage-owned titles and archive state. Workspace bindings gate launch. Discovery imports eligible workspaces through the [project identity resolver](docs/discovery.md). Projects can have several workspaces on a connection, with one primary. A clear move carries the binding forward. Ambiguity goes to review, and unbinding records a decline on that connection. Merge keeps an alias for the source ID. Split puts one workspace into a new project. Add a workspace in the harness, then refresh discovery to bind it. External removal preserves Stage history.
- Every harness is optional; a first run has no connections and there is no default harness: a task or schedule runs on the connection its project, the default connection or the user names, with that harness's execution config. A compact Dashboard "Connect a harness" alert, shown whenever nothing is connected, links to Settings > Connections. Each connection has setup and diagnostics. A user can plan work before connecting any service. Connections are set up in Settings only, never from environment variables.
- Task states: backlog, launching, running, needs input, done, failed, interrupted, cancelled.
- Task actions: start, stop, duplicate, archive/unarchive, delete unstarted work without recorded history, and opening the selected harness. Adopted sessions are stopped or opened there, never started or duplicated by Stage.
- Pending questions: Needs-input tasks and notifications open the source harness for questions, permission approvals and follow-ups. Codex and Claude Code have no link to open: task rows, notifications and task detail offer Copy resume command (`cd <dir> && codex resume <id>`, `claude attach <id>`) to run in a terminal. Where the harness lets Stage answer (Claude Code, for the sessions Stage launches), task detail lists the pending approvals and questions to answer in Stage, and a needs-input row answers a single approval inline (Allow / Deny) or links to the task (Answer). Where the harness takes messages (Claude Code), task detail sends a follow-up to a finished session, or a reply when its turn ended asking the user. The harness's own client keeps answering; only the user answers or sends, never an agent.
- Screenshots: images dropped on (or picked for) the prompt are sent with it on every launch, where the connection offers images (its `images` operation; elsewhere the form names the reason); read-only once the task leaves backlog.
- Trees: a tree is a DAG of tasks (may span projects); a task's needs are tree members that require user completion first. Tree start mode auto launches a task once the user completes its needs; manual marks it ready (Ready group and stat cell, a `ready` notification with Start). A task may override the mode. Roots never auto-launch and read ready. Close work: Mark done (the rest will not be worked on; members keep their states, nothing more starts) or Archive a tree, Reopen/Unarchive to undo; not while a member is launching, running or needs input. Closed trees require explicit reopening. Done and archived trees, their tasks and archived tasks leave the Dashboard and default lists. Delete a tree (with its tasks) only when no member started and no recorded work exists. Protection survives tasks leaving. Dissolve detaches tasks and archives the tree; emptying also archives it, preserving identity and journal. Views: the Trees view (sidebar and phone tab; Open | Closed | All, a stat strip by each tree's next step, Active trees most pressing first and Completed in the last 7 days, rows expanding to their members; last activity and created date per tree), tree view (graph list in level order with time in state per task, or a List | Graph toggle to a top-down layered graph (step bands, solid/dashed need arrows), side panel: tree Activity feed or the selected task), a Tree panel on task detail (mini levels, needs, dependents, start mode, handoff; Add to tree when outside one), Dependents remain blocked until their needs are accepted. Removing a task splices it out (its dependents take its needs). An existing harness session can be tracked as a task (adopted: Track session on Stage or a project, or Add session in a tree) so it can be a node; stage never starts, restarts or duplicates it, and its prompt is read from its harness.
- Handoff uses a Stage snapshot of each accepted result. The successor prompt includes the bounded final reply, task and journal references, branch or worktree, and the session ID and link when available. The source harness can be offline.
- Where a session starts is a harness launch option the harness declares and Stage only passes on: T3 a new worktree with a base ref and branch; Claude Code and OpenCode a harness-managed worktree; Codex the project root only (no worktrees, no Plan mode; images are sent with the prompt). A dependent does not start from its predecessor's branch: the handoff carries the branch the predecessor reported.
- Scheduling: a backlog task can start at a time (one-shot, IANA zone, starts late after downtime; never together with needs). A schedule is a recurring template (presets or 5-field cron, own zone) that spawns and starts a new task per fire; skipped while the previous run is pending/running/needs input; fires missed while down are skipped. No new notifications.
- Sessions: Track session accepts a link or ID on the selected harness (the field hint says which forms; Codex: a thread id or a `codex resume <id>` command; Claude Code: a session UUID, the 8-character ID `claude agents` shows, or a pasted `claude attach` / `--resume` command). Sessions T3 started (its Codex threads, its Claude sessions) are refused: track them through T3. Preview title, project and state; confirm with an optional task title and initial journal note. Existing owners are reused. No global session browser.
- Journals: append-only task/tree notes and events with immutable IDs and provenance. Optional categories (finding, decision, blocker, outcome), text/task filters, cursor pagination, 600-rune previews and full-entry reads. Task notes follow current membership in tree aggregates; tree notes/events remain in their original tree. Moves log both IDs in both trees. Closed work accepts notes without reopening or scheduling. Initial notes on creation/adoption; schedules retain note templates; duplicates copy no notes. API v2 discards old task notes, preserves task event history, and starts accurate tree history at rollout. Agents use read_journal, get_journal_entry, append_note (CLI task notes / tree notes). Every launch receives persisted, retry-stable instructions to refresh membership, read context, checkpoint risky work, and record outcomes; notes are not instructions/proof, failed writes must be reported, and handoff is independent. No retroactive messages to existing/adopted sessions.
- Transcript: Conversations, detailed runs and session history stay in the source harness. Stage retains the adopted task opening prompt and its bounded final reply.
- Last word: Task detail retains the latest assistant reply as sanitized markdown (4000 characters, longer replies link to the harness). Task rows show a one-line preview. Cached replies remain available when the harness is offline. Reply polling only runs for task-owned sessions at rest when their updated time changed.
- Navigation: a laptop sidebar (phone: a scope chip and bottom tabs) holds Dashboard, Tasks, Trees and Schedules and a per-device project scope that filters all four. Projects are listed by recent activity, with pinned projects first (per device) and projects without open work folded as quiet; each shows its open work (needs input, what else asks for the user, running).
- Dashboard: only what asks for the user (Needs input, Awaiting review, Ready, Failed / interrupted), every task on its own row with a tree chip for tree members, then In flight counts (Running, Scheduled in 24h, Backlog) that open Tasks.
- Tasks: the place to browse work. Open | Closed | All, and All tasks | Not in a tree; every task by state, tree members linking their tree (opened with the task selected). A stat strip filters to one group. Completed holds the last 7 days of accepted work. Trees live in their own view.
- History: Global session/history browsing is retired. Task and tree journals retain their recorded history.
- Agent interface: CLI and MCP manage tasks, trees, journals and schedules. Explicit session adoption and read_ref remain. list_tasks with originSession (CLI task ls --origin-connection ID --origin-session ID) lists the tasks created by a session. Conversation actions belong in the source harness.
- References: Task headers copy markdown references or bare URLs. Task rows and the palette copy task links. read_ref / stage show resolve task references and explicitly named sessions. Historical session references resolve to their owning task or native harness destination. References remain context, never dependencies.
- Snippets: reusable prompt text, global or scoped to one project, inserted by typing `/` in a prompt or notes. Settings: connection (state, T3 identity; T3 counts as connected only when paired; Disconnect, never locked: forgets the token, T3 URL, Browser URL and admin token and stops syncing; pairing the same T3 resumes, pairing another replaces the connection and keeps its tasks read-only), previous connections (replaced instances with their task counts; Forget lets one go and keeps its history), pairing (one click through the local t3 CLI, or a code), T3 URL, Browser URL (for Open in T3 links; empty = T3 URL) and optional admin token (renews the T3 token automatically; never shown), OpenCode connection (one-click Connect to the OpenCode service on this machine with its own password, a pairing link from `opencode pair` whose session renews automatically, or a plain address with a password when asked; Disconnect forgets it; tasks and history stay), Codex connection (Connect starts the daemon when it is down; versions, account, CODEX_HOME and daemon state; when not connected, the reason and the command that fixes it; the Codex CLI path; Disconnect stops tracking, the daemon and its threads stay), Claude Code connection (Connect checks the claude command and its login; which Claude it uses; Check connection; Claude command; Disconnect keeps tasks and history), sync now, global notification event filter (needs input / failed / ready / done; unchecked events are dropped from inbox, push and desktop notifications), per-device notifications (Web Push in the browser, a native on/off on desktop, on by default).

## Brand Commitments
- Name: stage (lowercase).
- User-pinned visual direction: inspired by zed.dev and px0.ai; sharp borders, mildly colored borders; Ink accent (black on white / near-white on near-black); pure white light mode; color only on states; Geist UI text with JetBrains Mono for metadata.

## Evidence on Hand
Real data lives in the user's T3 instance; there are no testimonials, customers, or metrics to show and none should be invented.

## Product Principles
1. Needs-input is never missable: it leads every view it appears in.
2. The selected harness stays authoritative for conversations and approvals: Stage answers approvals and questions only where the harness allows it, and its own client keeps working. Stage retains accepted results and journals. Every task links straight to its session, or copies its resume command.
3. Phone and laptop are both first-class; phone gets the glance and the quick action.
4. Dense and scannable over decorative; state carries the color.

Pre-existing external T3 sessions waiting for input appear as silent current-state rows in the inbox when they have no recorded notification group. They add no unread event, push, toast or synthetic history. A recorded group replaces the silent row.
