# Product

<!-- impeccable:product-schema 1 -->

## Platform

web

## Users
Developers running many T3 Code agent threads across several projects. They use stage mostly from a laptop and a phone on their private network, rarely a desktop: queueing work, checking what needs input, and glancing at what is running or done.

## Product Purpose
A self-hosted stage manager for T3 Code. It queues tasks (prompt + provider/model/effort + runtime/workspace), launches them as T3 threads, tracks thread status, runs task trees (a task starts when every task it needs is settled in T3), and gives a cross-project history of every T3 thread. Success: never miss a thread that needs input, keep a queue moving without babysitting, and see recent work at a glance.

## Positioning
Sits beside T3 rather than replacing it: T3 remains where conversations happen ("Open in T3"); stage owns the queue, trees, and the cross-project view T3 does not provide. The one exception is a session's pending question: stage shows it and lets the user answer it in place, so a needs-input thread can be unblocked from a phone in one step.

## Operating Context
- Self-hosted on the T3 host via docker compose, listening on 127.0.0.1:7380 by default (compose publishes it on host loopback; expose it only on a trusted private network or behind a proxy), no auth.
- Or as a per-user OS service with the Linux/macOS desktop app: the same UI in a native window over the local Unix socket; the app starts the service, stays resident when its window closes and shows native notifications and a needs-input badge while resident; Quit stops them and leaves the server running. Phones and other machines keep using the browser.
- Talks to T3 only through T3's MCP endpoint; polls active tasks every 5s, full sync every 5 min, watched transcripts every 2s while their run is active.
- Settling a thread happens in T3, not here; dependent tasks wait for it.

## Capabilities and Constraints
- Projects mirror T3 projects 1:1; existing T3 projects import automatically.
- Task states: backlog, launching, running, needs input, done, settled, failed, interrupted, cancelled.
- Task actions: start/restart, follow-up (auto/queue/steer/restart, or with images), stop, duplicate, archive/unarchive (standalone tasks), delete (only a task that never started: no launch, no session), open in T3.
- Pending questions: a session waiting on T3 user input shows a Needs input panel at the top of task and session detail (single/multi select, own answer, one Send answer per request). Rows, toasts and inbox entries get Answer; needs-input pushes deep link to the panel. Approvals cannot be answered here: the panel counts them and links to T3. Sync counts answerable questions per waiting thread; questions are read fresh when shown. A resent answer is idempotent; answered-elsewhere and stale requests say so. Agents can read questions (CLI/MCP), not answer them.
- Screenshots: images dropped on (or picked for) the prompt are sent with it on every launch; read-only once the task leaves backlog.
- Trees: a tree is a DAG of tasks (may span projects); a task's needs are tree members that must settle first. Tree start mode auto launches a task once its needs settle; manual marks it ready (Ready group and stat cell, a `ready` notification with Start). A task may override the mode. Roots never auto-launch and read ready. Close work: Mark done (the rest will not be worked on; members keep their states, nothing more starts) or Archive a tree, Reopen/Unarchive to undo; not while a member is launching, running or needs input. Activity on a member (T3 restart, Start, follow-up) reopens the tree; an archived task unarchives the same way. Done and archived trees, their tasks and archived tasks leave the Dashboard and default lists. Delete a tree (with its tasks) only when none started; Dissolve keeps the tasks. Views: Trees list (Active | Done | Archived | All; last activity and created date per tree), tree view (graph list in level order with time in state per task, hover trace, side panel: tree Activity feed or the selected task), a Tree panel on task detail (mini levels, needs, dependents, start mode, base, handoff; Add to tree when outside one), New tree from a session batch selection (Parallel or Chain). A failed need keeps dependents blocked; Start early runs a blocked task anyway. Removing a task splices it out (its dependents take its needs). An existing T3 session can be tracked as a task (adopted: Track as task on session detail, or Add session in a tree) so it can be a node; stage never starts, restarts or duplicates it, and its prompt is read from T3.
- Handoff: on by default per task (form toggle; REST, CLI and MCP flag). When a task with needs launches, stage reads each finished need live from T3 and appends one block per need to the prompt: final reply (4000 chars, less when there are several needs; truncation marked), PR links with state, branch/worktree, thread id and link. Composed at launch; each attempt's block is stored and shown in the task's Prompt panel (backlog shows what will be appended). A failed read never blocks the launch: it launches bare and records why.
- Predecessor base: opt-in per task (Workspace "#12's branch" cell, shown in the form for a task with needs; REST, CLI and MCP `base: predecessor`, `baseTaskId` picks the need). The task's T3 worktree starts from a need's branch (local ref, unpushed commits included), so stacked work builds on unmerged changes. Falls back to the task's own base ref, with a task event and reason, when there is no single need to pick, or the need ran at root, in another project, has no branch, has only merged PRs, or T3 rejects the branch; the launch is never blocked. Task detail shows the planned base, then the base the launch used.
- Scheduling: a backlog task can start at a time (one-shot, IANA zone, starts late after downtime; never together with needs). A schedule is a recurring template (presets or 5-field cron, own zone) that spawns and starts a new task per fire; skipped while the previous run is pending/running/needs input; fires missed while down are skipped. No new notifications.
- Sessions: Active and All views across the connected T3 instance, paginated and ordered by recent activity. Active has no creation cutoff. Session detail exposes the opening prompt (the linked task's prompt and images, else the session's first own message read live from T3; first in Overview, clamped, above Last word, same as task detail), live state, workspace, related task, children, and the tasks the session created (Created tasks: grouped by tree, then independent tasks; start or edit a task). Task detail shows the same batch as a compact Batch panel linking back to it. Children are inspectable. The Ctrl K palette (and `stage sessions search`) finds sessions by title, then by branch, PR, project or message text via T3's thread search; offline it falls back to titles.
- Transcript: session and task detail switch between Overview and a read-only Transcript (user/assistant messages and plans only, safe markdown, collapsed long messages, newest 50 with Load earlier). Live over SSE while a run is active; the server polls T3 only while a run is active and someone watches. Full detail (tools, commands, diffs) stays in T3.
- Last word: each session's latest assistant reply, read during sync only when a thread is at rest and its updatedAt changed; stored as a 4000-char excerpt (truncated replies link to T3) plus a one-line preview. Task and session detail show the excerpt as sanitized markdown; Needs input and Done rows (dashboard, project, sessions) show the preview as one clamped line. A running thread keeps its previous reply. Agents get it via get_task/get_session (excerpt) and list rows (preview). Read-only; replying stays in T3.
- Pull requests and runs: PRs T3 associates with a thread are mirrored on every sync and shown as state chips on task and session rows (Dashboard, Project, Sessions, History; two, then +n) and as a list on task and session detail linking to the PR (open sky, merged green, closed/draft gray). Task and session detail show a Runs panel (each follow-up is a new run): ordinal, status, model, start, run time, queue time; five newest, Show all for up to 50 stored. REST, `get_task`/`get_session` and CLI show expose both.
- Dashboard: a Trees group of tree rows (segmented state bar, next step, Start ready) rolls up tree members out of the state groups; members that need input or are ready also keep their own row with a tree chip. Settled (last 7 days): tasks, external T3 threads and completed trees in one list, newest settle first, each with its settle time and elapsed run time.
- History: all mirrored threads (often hundreds, many of them subagent threads), time-window and attribute filters.
- Agent interface: agents (and scripts) manage tasks through the `stage` CLI (`--json`), a stdio MCP server (`stage mcp`) or HTTP MCP at `/mcp`, all over the REST API. Create backlog tasks, start/stop/follow up, build trees and set needs (incl. "after me": the calling session is tracked as a task and needed), track a session as a task, schedules, session reads (incl. the tasks the session created, so a planning agent can verify its batch). The calling session and cwd pick the project; tasks and schedules record the session that created them (shown as "Created by" / "by agent").
- References: task and session detail copy a self-describing markdown link (Copy link) or the bare URL; laptop rows copy on a hover icon; the palette copies with Alt C. Agents resolve a pasted link (stage link on any host, T3 thread link, #id, thread id) with `read_ref` / `stage show`, getting the task and/or session plus a pointer to `t3_thread_read`. Pasted stage links render as live chips in prompts, transcript user messages, last word and handoff. A reference is context only, never a tree dependency.
- Snippets: reusable prompt text, global or scoped to one project, inserted by typing `/` in a prompt, follow-up or notes. Settings: connection, pairing, sync now, global notification event filter (needs input / failed / ready / done / settled; unchecked events are dropped from inbox, push and desktop notifications), per-device notifications (Web Push in the browser, a native on/off on desktop, on by default).

## Brand Commitments
- Name: stage (lowercase).
- User-pinned visual direction: inspired by zed.dev and px0.ai; sharp borders, mildly colored borders; Ink accent (black on white / near-white on near-black); pure white light mode; color only on states; Geist UI text with JetBrains Mono for metadata.

## Evidence on Hand
Real data lives in the user's T3 instance; there are no testimonials, customers, or metrics to show and none should be invented.

## Product Principles
1. Needs-input is never missable: it leads every view it appears in.
2. T3 is the place to talk; stage is the place to queue, watch and answer what blocks a thread. Every task links straight to its thread.
3. Phone and laptop are both first-class; phone gets the glance and the quick action.
4. Dense and scannable over decorative; state carries the color.
