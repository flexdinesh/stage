# Product

<!-- impeccable:product-schema 1 -->

## Platform

web

## Users
Developers running T3 Code, OpenCode, Codex and Claude Code sessions across several projects. They use stage mostly from a laptop and a phone on their private network, rarely a desktop: queueing work, checking what needs input, and glancing at what is running or done.

## Product Purpose
A self-hosted task manager for T3 Code, OpenCode V2, Codex and Claude Code. Users plan tasks, review final replies, complete work and start ready dependents across projects.

## Positioning
Stage owns logical project groups, tasks, trees, schedules, journals, acceptance and durable handoff: it launches a task into a harness and keeps up with its progress. T3, OpenCode, Codex and Claude Code own sessions and everything in them: conversations, questions, approvals, execution, workspace catalogs, worktrees and branches ([ADR 0010](docs/adr/0010-harness-workspaces-and-logical-projects.md)). Stage-wide features work across harnesses or adapt to declared capabilities, while each harness keeps its own scoped extras, settings, setup panel and vocabulary ([ADR 0008 P2–P3](docs/adr/0008-harness-foundation.md#p2)).

## Operating Context
- Personal is the default. The local desktop socket and trusted home LAN can run Stage and its workers without signing in. Anyone who reaches a personal listener can operate Stage. The default Compose setup publishes only on host loopback.
- An installation owner can enable [shared access](docs/runtime.md#shared-setup-and-owner-recovery) for one trusted workspace across projects, workers and harnesses. People sign in with email and password and admins share single-use invites. All members can run code where their harnesses permit. OS accounts and hosts are the isolation boundary.
- Or as a per-user OS service with the Linux/macOS desktop app: the same UI in a native window over the local Unix socket; the app starts the service, stays resident when its window closes and shows native notifications and a needs-input badge while resident; Quit stops them and leaves the server running. Phones and other machines keep using the browser.
- The desktop app opens this machine's server by default. Add or switch to a remote in Settings > General > Servers. For shared access, use the server's canonical HTTPS URL and sign in separately on desktop. Each Stage server owns its harness connections.
- One existing T3 MCP service and one existing OpenCode V2 service may be used independently or together. Each instance (a T3 environment, an OpenCode service) is its own connection; one per harness is active on each machine. Replacing an instance preserves the old connection's recorded work. Select an exact workspace on the new connection for future launches, or reconnect the original instance.
- Codex is hosted: Stage drives the Codex app-server daemon on the machine it runs on (desktop app, or `stage serve --local-harnesses`) or on a worker with local harnesses (the worker service, or `stage worker run --local-harnesses`), never in Docker. Connect starts the daemon when it is down. Stage never stops it and stores no Codex credentials (`codex login`). Its connection is the Codex home. Users can answer command, file-change and permission approvals in Stage on a supported daemon. Messages start a new turn once a thread is idle. Questions and MCP elicitations are answered in Codex through a copied `codex resume` command.
- Claude Code runs as Claude background sessions (`claude --bg`) on the machine Stage runs on (the desktop app, or `stage serve --local-harnesses`) or on a worker with local harnesses (the worker service, or `stage worker run --local-harnesses`), never in Docker, signed in with Claude's own login; Stage stores no Claude credentials. Its connection is named by Claude's config folder.
- Only acceptance in Stage releases dependent tasks: completion by the user or by an agent (never its own task), or a per-connection auto-complete (on by default) when a successful run's T3 thread is settled, OpenCode session or Codex thread is archived, or Claude Code session is removed (`claude rm`). New trees default to auto start; tasks inherit.

## Capabilities and Constraints
- Projects have stable Stage IDs, titles and archive state. Discovery groups exact catalog rows using strong evidence. The Workspaces panel shows each row's connection and status. Move or separate individual rows. Old IDs, aliases, snippets, recorded project attribution and launch pins remain addressable. [Workspace grouping](docs/discovery.md)
- Every harness is optional. A first run has no connections. Plan backlog work before selecting a workspace. Immediate and timed starts and recurring schedules require an exact workspace on the chosen connection. The default connection can prefill the form. A Dashboard alert links to Settings > Connections while nothing is connected.
- Task states: backlog, launching, running, needs input, done, failed, interrupted, cancelled.
- Task actions: Task holds start/restart, edit, duplicate, archive/unarchive and eligible deletion. The current Session holds stop, opening or resuming the harness, and declared session actions. Adopted sessions can be stopped or opened where available.
- Pending questions: The needs-input alert stays above Task and Session. Row and notification links go to Session. Where `respond` is declared, Requests leads there. A row can answer a single approval inline or link to the full requests. The harness continues to answer in its own client. Session messages use the connection’s native `steer` or `queue` during a turn, and `send` once the turn ends and any answerable requests are cleared. Agents can answer or message another task’s session.
- Screenshots: images dropped on (or picked for) the prompt are sent with it on every launch, where the connection offers images (its `images` operation; elsewhere the form names the reason); read-only once the task leaves backlog.
- Trees: a tree is a DAG of tasks (may span projects); a task's needs are tree members that require completion in Stage first. Tree start mode auto launches a task once its needs are completed; manual marks it ready (Ready group and stat cell, a `ready` notification with Start). A task may override the mode. Roots never auto-launch and read ready. Close work: Mark done (the rest will not be worked on; members keep their states, nothing more starts) or Archive a tree, Reopen/Unarchive to undo; not while a member is launching, running or needs input. Closed trees require explicit reopening. Done and archived trees, their tasks and archived tasks leave the Dashboard and default lists. Delete a tree (with its tasks) only when no member started and no recorded work exists. Protection survives tasks leaving. Dissolve detaches tasks and archives the tree; emptying also archives it, preserving identity and journal. Views: the Trees view (sidebar and phone tab; Open | Closed | All, a stat strip by each tree's next step, Active trees most pressing first and Completed in the last 7 days, rows expanding to their members; last activity and created date per tree), tree view (graph list in level order with time in state per task, or a List | Graph toggle to a top-down layered graph (step bands, solid/dashed need arrows), side panel: tree Activity feed or the selected task), a Tree panel on task detail (mini levels, needs, dependents, start mode, handoff; Add to tree when outside one), Dependents remain blocked until their needs are accepted. Removing a task splices it out (its dependents take its needs). An existing harness session can be tracked as a task (adopted: Track session on Stage or a project, or Add session in a tree) so it can be a node; stage never starts, restarts or duplicates it, and its prompt is read from its harness.
- Handoff uses a Stage snapshot of each accepted result. The successor prompt includes the bounded final reply, task and journal references, branch or worktree, and the session ID and link when available. The source harness can be offline.
- Where a session starts is a harness launch option the harness declares and Stage only passes on: T3 a new worktree with a base ref and branch; Claude Code and OpenCode a harness-managed worktree; Codex the project root only (no worktrees, no Plan mode; images are sent with the prompt). A dependent does not start from its predecessor's branch: the handoff carries the branch the predecessor reported.
- Scheduling: a backlog task can start at a time (one-shot, IANA zone, starts late after downtime; never together with needs). A schedule is a recurring template (presets or 5-field cron, own zone) that pins a connection and workspace and starts a new task per fire. Fires are skipped while the previous run is pending, running or needs input, or when the destination needs repair. Fires missed while down are skipped. No new notifications.
- Sessions: Track session searches the selected connection's current roster where supported, including listed completed sessions. Results show workspace and start time when available. Use a link or ID for a named lookup. The field hints show supported forms, including Codex thread IDs and resume commands and Claude Code session IDs and attach commands. Sessions T3 started are tracked through T3. Preview the session and confirm with an optional task title and initial journal note. Stage can track a verified workspace without selecting a launch destination. Open already tracked tasks from the picker and confirm tree changes separately.
- Journals: append-only task/tree notes and events with immutable IDs and provenance. Optional categories (finding, decision, blocker, outcome), text/task filters, cursor pagination, 600-rune previews and full-entry reads. Task notes follow current membership in tree aggregates; tree notes/events remain in their original tree. Moves log both IDs in both trees. Closed work accepts notes without reopening or scheduling. Initial notes on creation/adoption; schedules retain note templates; duplicates copy no notes. API v2 discards old task notes, preserves task event history, and starts accurate tree history at rollout. Agents use read_journal, get_journal_entry, append_note (CLI task notes / tree notes). Every launch receives persisted, retry-stable instructions to refresh membership, read context, checkpoint risky work, and record outcomes; notes are not instructions/proof, failed writes must be reported, and handoff is independent. No retroactive messages to existing/adopted sessions.
- Transcript: Full conversations and detailed runs stay in the source harness. Session shows bounded recent activity where available and links to its full transcript. Attempts are listed newest first. Earlier attempts show read-only snapshots. [Session surface](docs/adr/0014-session-surface.md)
- Last word: Session shows the selected attempt’s latest assistant reply as sanitized markdown (4000 characters). Longer replies link to the harness. Task rows show a one-line preview. Cached replies remain available when the harness is offline. Reply polling runs for task-owned sessions at rest when their updated time changes.
- Navigation: a laptop sidebar (phone: a scope chip and bottom tabs) holds Dashboard, Tasks, Trees and Schedules and a per-device project scope that filters all four. Projects are listed by recent activity, with pinned projects first (per device) and projects without open work folded as quiet; each shows its open work (needs input, what else asks for the user, running). Task detail defaults to its Task tab. The Session tab and recorded attempts have shareable URLs on phone and laptop.
- Dashboard: what asks for the user, then work in motion (Needs input, Awaiting review, Failed / interrupted, Running, Ready). A task outside a tree has its own row; a tree member shows only through its open tree's row (the Trees view row), listed once under the tree's most pressing step; waiting, completed and closed trees stay off. Then In flight counts of tasks outside trees (Scheduled in 24h, Backlog) that open Tasks.
- Tasks: the place to browse work. Open | Closed | All, and All tasks | Not in a tree; every task by state, tree members linking their tree (opened with the task selected). A stat strip filters to one group. Completed holds the last 7 days of accepted work. Trees live in their own view.
- History: Global session/history browsing is retired. Task and tree journals retain their recorded history.
- Agent interface: CLI and MCP manage tasks, trees, journals, schedules, projects, group membership and snippets, and complete, reopen, answer or message other tasks, never their own ([ADR 0011](docs/adr/0011-agent-operation-parity.md)). Explicit session adoption and read_ref remain. list_tasks with originSession (CLI task ls --origin-connection ID --origin-session ID) lists the tasks created by a session. The source harness owns the conversation and declares the operations Stage can relay.
- References: Task headers copy markdown references or bare URLs. Task rows and the palette copy task links. read_ref / stage show resolve task references and explicitly named sessions. A recorded past session resolves to its owning task and attempt. References remain context, never dependencies.
- Snippets: reusable prompt text, global or scoped to one project, inserted by typing `/` in a prompt or notes. Settings: connection (state, T3 identity; T3 counts as connected only when paired; Disconnect, never locked: forgets the token, T3 URL, Browser URL and admin token and stops syncing; pairing the same T3 resumes, pairing another replaces the connection and keeps its tasks read-only), previous connections (replaced instances with their task counts; Forget lets one go and keeps its history), pairing (one click through the local t3 CLI, or a code), T3 URL, Browser URL (for Open in T3 links; empty = T3 URL) and optional admin token (renews the T3 token automatically; never shown), OpenCode connection (one-click Connect to the OpenCode service on this machine with its own password, a pairing link from `opencode pair` whose session renews automatically, or a plain address with a password when asked; Disconnect forgets it; tasks and history stay), Codex connection (Connect starts the daemon when it is down; versions, account, CODEX_HOME and daemon state; when not connected, the reason and the command that fixes it; the Codex CLI path; Disconnect stops tracking, the daemon and its threads stay), Claude Code connection (Connect checks the claude command and its login; which Claude it uses; Check connection; Claude command; Disconnect keeps tasks and history), sync now, global notification event filter (needs input / failed / ready / done; unchecked events are dropped from inbox, push and desktop notifications), per-device notifications (Web Push in the browser, a native on/off on desktop, on by default).

## Brand Commitments
- Name: stage (lowercase).
- User-pinned visual direction: inspired by zed.dev and px0.ai; sharp borders, mildly colored borders; Ink accent (black on white / near-white on near-black); pure white light mode; color only on states; Geist UI text with JetBrains Mono for metadata.

## Evidence on Hand
Real data lives in the user's T3 instance; there are no testimonials, customers, or metrics to show and none should be invented.

## Product Principles
1. Needs-input is never missable: it leads every view it appears in.
2. The selected harness stays authoritative for conversations and approvals: Stage answers approvals and questions only where the harness allows it, and its own client keeps working. Stage retains accepted results and journals. Every task links straight to its session, or copies its resume command.
3. Phone and laptop are both first-class; phone gets the glance and the quick action.
4. Dense and scannable over decorative; state carries the color.

Pre-existing external T3 sessions waiting for input appear as silent current-state rows in the inbox when they have no recorded notification group. They add no unread event, push, toast or synthetic history. A recorded group replaces the silent row.
